01Motivation · 문제와 설계 목표

잘게 나눠 병렬화하되, 원래 부모와 순서를 잃지 않는다

한눈에 요약

PDF 한 건이 페이지 여러 장으로, 영상 한 편이 클립 여러 개로 바뀌면 각 자식을 따로 처리해야 GPU 병렬성이 살아납니다.

하지만 자식 수가 부모마다 다를 때 한 배치의 경계와 결과 순서를 부모 관계로 착각하면 재구성에 전역 셔플과 앱 코드가 필요합니다.

RayOrch가 풀려는 핵심은 물리 배치와 논리적인 문서 구조를 분리하는 일입니다.

기존 방식은 두 극단 사이에 있습니다. Ray Data의 flat_map이나 Daft의 explode는 자식을 펼쳐 병렬 처리를 열지만, 자식의 부모·순서를 앱이 들고 다니며 마지막에 다시 모아야 합니다. 반대로 문서 전체를 하나의 큰 작업으로 감싸면 자식 단위 GPU 병렬성이 가려집니다. 긴 꼬리(long tail)를 가진 입력에서는 일부 큰 문서가 전역 regroup 단계를 오래 붙잡을 수 있습니다.

논문은 이를 “multi-grain dataflow”로 정의합니다. 논리 데이터 단위가 단계마다 바뀌어도 각 부모의 자식 집합, 자식 순번, 결과 완료 상태를 유지하는 것이며, 본 논문의 구현 범위는 유한한 비순환 계층 구조입니다.

핵심 구분

배치는 “같이 실행된 묶음”이지 “같은 부모의 결과 묶음”이 아닙니다. 이 둘을 분리해야 자식을 여러 부모에서 모아 GPU를 채우면서도 부모별 결과를 정확히 복원할 수 있습니다.

02Programming Model · 프로그래밍 모델

확장과 수집을 짝으로 선언하고, 컴파일러가 구조를 확인한다

한눈에 요약

프로그램은 부모에서 자식으로 가는 확장과 자식에서 부모로 돌아오는 수집을 각각 선언합니다.

컴파일러가 두 연산의 도메인 관계를 검사하고, 런타임은 실제 자식 구성원과 순번을 기록합니다.

RayOrch는 처리 함수를 새로 발명하기보다, 평범한 함수 호출과 데이터 구조 연산을 분리해 선언합니다.

Domain은 Page처럼 데이터 단위의 구조적 종류이고, Entity는 그 도메인 안의 고유 단위입니다. Function은 재사용 코드, Call은 설정된 함수 적용, Grain은 한 Call이 한 Entity에 실행되는 작업입니다. Port는 논리 데이터 흐름이며, Item은 포트와 Entity에 대응하는 값입니다.

03Runtime Semantics · 실행·완료·실패

준비된 작업은 계속 진행하고, 완료 판정은 부모 단위로 한다

한눈에 요약

각 Call은 입력이 준비된 Grain을 FIFO 큐에 넣고, 다른 부모의 Grain과 섞어 물리 batch를 만들 수 있습니다.

결과는 generation-fenced commit을 거쳐 구조 상태에 반영되며, 완료 순서가 아니라 불변 ordinal로 복원됩니다.

런타임의 역할은 실행 순서를 보존하는 것이 아니라, 선언된 논리 구조의 완료를 정확히 판정하는 것입니다.

한 Grain의 성공 결과가 commit되면 여러 하위 Call의 준비 큐를 각각 활성화합니다. 각 Call은 큐와 actor pool을 독립적으로 운영하므로 한 Call의 긴 꼬리가 다른 Call의 준비 작업을 묶지 않습니다.

재시도와 worker 교체를 고려해 commit은 generation으로 fenced됩니다. 현재 세대의 Grain만 terminal outcome을 게시할 수 있고, 지연된 오래된 시도의 결과는 거부됩니다. 이렇게 해야 재실행이 중복 결과를 덮어쓰거나 부모의 완료 상태를 되돌리는 일이 없습니다.

논리 경계 parent-scoped reduction

  • 확장 시점의 membership을 사용
  • immutable ordinal로 결과 순서를 결정

물리 경계 batch / attempt

  • 어떤 Grain이 한 GPU batch에 들어가는지 결정
  • 재시도·완료 순서는 결과 구조를 결정하지 않음
실패 격리 범위

typed failure는 해당 Call과 immediate parent 안에서 아직 dispatch되지 않은 sibling 작업을 억제합니다. 이미 실행 중인 sibling 보고는 거부하고, 관계없는 부모는 계속 진행합니다. 이 규칙이 없으면 한 문서의 오류가 전체 batch나 pipeline을 불필요하게 멈출 수 있습니다.

04Evaluation · 성능과 적용 범위

64 GPU까지 확장되고, FIFO와 부모별 실패 억제가 추가 이득을 낸다

한눈에 요약

H20 GPU 실험에서 MinerU는 4→64 GPU에서 15.14배, 영상은 8→64 GPU에서 7.82배 처리 시간 speedup을 보였습니다.

성능은 Ray Data·Daft보다 나았지만, 유한한 비순환 fan-out/gather 파이프라인과 평가 환경에 한정해 읽어야 합니다.

논문은 세 가지 축을 분리합니다: end-to-end 시간, GPU 확장성, 그리고 실행 중단된 sibling 작업의 낭비 감소.

MinerU 데이터는 유효 174,744 페이지를 가진 3,689 PDF, 영상 workload는 104,952 클립을 가진 27,091 영상입니다. Docling 평가에는 PDF 2,000개가 사용됩니다. MinerU는 H20 GPU 4–64개, 영상은 8–64개에서 strong scaling을 비교합니다.

읽을 때의 경계 Limitations

RayOrch는 유한한 비순환 계층 fan-out과 parent-scoped gather를 대상으로 합니다. 일반 join, 여러 microbatch를 가로지르는 window, feedback loop까지 처리하는 범용 dataflow라고 주장하지 않습니다. 성능 수치는 H20 기반 문서·영상 파이프라인과 실험에 사용된 baseline 버전에 조건부입니다. UDF의 외부 부작용이 안정적으로 재실행 가능하다는 점도 retry 안전성의 전제입니다.

실무 요점

“입력을 flatten하고 나중에 알아서 group하라”는 계약 대신, 부모·ordinal·completion을 런타임이 소유할 수 있는지 검토하세요. 데이터 prep 시스템에서 correctness state가 throughput optimization과 같이 설계될 수 있음을 보여줍니다.

＋Glossary · 핵심 용어

핵심 용어 정리

계보Lineage

한 결과가 어떤 부모에서 어떤 순번으로 나왔는지를 추적하는 구조 관계.

확장Expansion

부모 하나에서 가변 개수의 순서 있는 자식 단위를 만드는 논리 연산.

GrainExecution grain

한 Call을 하나의 Entity에 실행하는 최소 논리 작업.

OrdinalImmutable ordinal

자식이 생성될 때 부여되어, 실행 완료 순서와 무관하게 결과를 정렬하는 번호.

Generation fenceGeneration-fenced commit

재시도 세대가 오래된 결과를 늦게 게시하지 못하게 막는 commit 확인.

Ready QueuePer-Call FIFO Ready Queue

입력이 준비된 Grain을 Call별 FIFO 순서로 모아 batch 생성에 쓰는 큐.

＋One-page Summary · 한 장 정리

이 논문을 한 장으로

01
부모-자식 멤버십과 ordinal을 payload 추측이 아니라 런타임 구조 상태로 둔다.
02
물리 batch는 여러 부모의 작업을 섞어도 되지만 논리 reduce는 선언된 membership으로 부모별 복원한다.
03
Call별 FIFO는 준비된 작업을 계속 공급하고, 한 부모의 긴 꼬리가 다른 부모를 막지 않게 한다.
04
generation fence와 typed failure는 재시도 결과·실패 범위를 각각 Grain, Call×parent로 제한한다.
05
평가에서는 64 GPU scaling뿐 아니라 workload, hardware, ablation, 실패 주입 조건을 함께 읽는다.
