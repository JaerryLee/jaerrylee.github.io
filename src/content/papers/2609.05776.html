문서를 찾는 것보다, 찾은 업무 규칙을 계산에 적용하는 일이 어렵다

한눈에 요약

기존 data agent benchmark는 SQL 계산 또는 문서 QA 한쪽에 치우쳐 있다.

DI-Bench는 database 계산에 business rule 문서가 실제로 결과를 바꾸는 731개 과제를 만든다.

기업 질문은 “매출이 얼마인가?”로 끝나지 않는다. “반품은 제외하고, 특정 시점 이후 규칙을 적용한 순매출”처럼 문서의 정책을 SQL 계산에 반영해야 한다.

02Graph · benchmark를 만드는 연결 지도

table·metric·rule·dimension을 연결해 함께 필요한 조합만 뽑는다

한눈에 요약

artifact linkage graph는 database schema와 문서의 업무 규칙 사이의 의존성을 표현한다.

connected subgraph를 뽑아 실행 가능한 task skeleton을 만들며, 특히 rule→metric edge가 문서와 계산을 잇는다.

여기서 graph는 agent가 답할 때 사용하는 GraphRAG가 아니라 benchmark 생성기가 과제 재료를 고르는 내부 지도다.

노드는 table, metric, rule document, dimension이다. 간선은 table–table join, table–dimension, metric–table, metric–metric, rule–metric, rule–dimension 등 여섯 종류다. 무작위 문서와 표를 묶으면 아무 관련 없는 문제가 되기 쉬우므로, 연결된 subgraph만 선택한다.

03Generation · 답부터 만든 뒤 질문을 쓴다

SQL 실행으로 gold answer를 고정하고 자연어 질문을 역으로 생성한다

한눈에 요약

선택한 subgraph에서 분석 template을 SQL로 구체화하고 실제 database에서 답을 실행한다.

rule이 있는 과제는 적용 전후 답이 달라지는 counterfactual check를 통과해야 한다.

먼저 분석 유형과 dimension을 넣어 base SQL을 만든다. rule 문서에서 filter·exclude·threshold·weight·override 같은 연산을 뽑아 SQL에 적용한다. rule을 적용해도 답이 같으면 그 rule은 과제에 실질적으로 필요하지 않으므로 버린다.

LLM은 task skeleton, gold answer, schema·metric·rule을 보고 자연어 질문을 쓴다. 이후 실행 가능성, answer leakage, 형식, 자연스러움, scope, reasoning 품질 등을 programmatic filter와 LLM validator로 검사한다. 답을 LLM judge의 의견으로 정하지 않고 SQL execution으로 고정한 점이 강점이다.

초등학생도 이해하는 설명

보통은 문제를 먼저 쓰고 답을 사람이 계산한다. 여기서는 컴퓨터가 표와 규칙으로 정답을 먼저 확실히 계산한 다음, 그 정답을 물어보는 자연스러운 문제 문장을 만든다. 규칙을 빼도 답이 같으면 가짜 규칙 문제라서 버린다.

06Implications & Limits · 검색 다음의 reasoning

검색 평가를 ‘정답 문서를 찾았나’에서 ‘행동을 바꿨나’로 넓힌다

한눈에 요약

기업 RAG는 rule citation뿐 아니라 rule을 계산 계획에 적용한 결과까지 평가해야 한다.

두 공개 domain·합성 artifact·exact match·일부 희소 task type이라는 한계가 있다.

검색 시스템 관점에서 가장 중요한 메시지는 retrieval success와 task success 사이에 rule execution layer가 있다는 것이다.

실무 benchmark라면 정답 rule recall, rule 해석, SQL/도구 계획 수정, 실행 결과를 단계별로 관측해야 한다. query rewriting이나 reranking만 개선해도 oracle-rule 결과가 비슷하다면 병목은 그대로 남는다. 이 경우 rule을 구조화된 연산으로 compile하거나, 계획 전후를 검증하는 executor가 더 우선이다.

한계는 Brazilian e-commerce와 Czech finance 두 domain뿐이고, metric·rule 문서는 합성이다. exact match는 부분적으로 맞은 계산을 인정하지 않는다. 일부 분석 유형은 표본이 적고, 생성 LLM과 validator가 benchmark 표현을 좌우한다. 다른 retriever·agent architecture를 체계적으로 바꾸는 실험도 없다.

초등학생도 이해하는 설명

책을 잘 찾아온 학생에게 바로 100점을 주면 안 된다. 책의 규칙을 실제 계산에 써서 답이 바뀌었는지까지 봐야 한다. 다만 이 문제집은 가게와 은행 두 종류만 연습했으므로 모든 회사 일을 대표하지는 않는다.

＋Retrieval Family · 검색 계열 1차 판별

GraphRAG가 아니라 graph로 RAG·agent benchmark를 생성하는 방법이다

한눈에 요약

subgraph가 나오지만 runtime 답변 검색용 path retrieval은 아니다.

agent가 평가 중 이 graph를 보거나 Microsoft GraphRAG·HippoRAG 절차를 실행하지 않는다.

community report · global/local search · DRIFT가 없으므로 Microsoft GraphRAG가 아니다. PPR · passage node · associative memory도 없다. subgraph라는 단어는 나오지만 benchmark 출제 재료를 묶는 데 사용한다. HNSW·Vamana처럼 vector 검색을 빠르게 하는 ANN graph도 아니다. 분류하면 graph-guided benchmark generation for retrieval-and-tool agents다.

초등학생도 이해하는 설명

지도는 시험 보는 학생에게 주는 검색 도구가 아니라, 선생님이 서로 관련된 문제 재료를 고르는 출제 도구다. 같은 ‘graph’라는 단어라도 쓰는 사람이 다르다.

＋Glossary · 핵심 용어

핵심 용어 정리

Artifact업무 산출물

table, metric 정의, rule 문서, dimension처럼 질문에 필요한 자료다.

Task skeleton과제 골격

어떤 표·지표·규칙·분석 연산을 써야 하는지 정한 구조다.

Gold answer정답

LLM 추측이 아니라 SQL을 실행해 결정한 기준 답이다.

Counterfactual check반사실 검사
