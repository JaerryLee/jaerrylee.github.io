01Motivation · 문제

클라우드 MPI의 문제

한눈에 요약

Spot/preemptible instance는 최대 90% 할인될 수 있지만 자원이 회수된다. MPI rank는 network state와 tightly coupled communicator를 가져 일반 checkpoint만으로 옮기기 어렵다.

영향 받은 rank만 이동시키고 나머지는 잠시 quiesce한다. MPI Sessions로 network resource를 teardown·reconstruct하고 Hydra가 proxy replacement와 KVS reconnect를 조정한다.

02Design · 설계

Sessions와 migration 구조

한눈에 요약

애플리케이션은 자연스러운 iteration boundary에서 XMPI_quiesce를 호출한다. 모든 rank가 session을 종료·대기한 뒤 새 session과 communicator를 만든다.

checkpoint 대상이 아닌 TCP/RDMA state는 teardown 후 재구성한다. launcher–proxy control channel은 TCP이고 proxy replacement는 fd swap과 KVS address exchange를 사용한다.

03Evaluation · 평가

실행 오버헤드

한눈에 요약

네 proxy application을 9-node cluster에서 평가했다. quiesce는 전체 downtime의 1.4% 미만이고 정상 instrumentation overhead는 noise 수준이었다.

XMPIaaS는 LULESH 3.8% faster, HPCCG 1.0% faster인 경우도 있지만 CoMD 9.8%, miniAMR 14.2% slower였다. 목표는 계산 가속이 아니라 중단·복구 가능성이다.

04Migration · 결과

선택적 이동 비용

한눈에 요약

rank footprint에 따라 migration은 0.3–6.2초이고 반복 8회 downtime은 약 1,012ms로 안정됐다. downtime은 job 전체보다 이동 node의 rank 수에 좌우됐다.

image transfer가 60–92%를 차지했고 non-migrating rank는 checkpoint하지 않는다. evacuation width와 per-node rank density를 바꿔도 선택적 checkpoint가 유리했다.

05Limits · 한계

범위와 한계

한눈에 요약

애플리케이션이 cooperative quiesce 지점을 제공해야 하고 RDMA·device-backed mapping 상태는 여전히 제약이다. 다른 MPI 구현과 proxy tree는 후속 과제다.

full transparency인 MANA와 달리 application cooperation을 요구한다. MPI Sessions와 Hydra 공통 abstraction에 기대므로 Open MPI·다른 cloud scheduler에서 state contract를 재검증해야 한다.
