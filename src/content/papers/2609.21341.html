01System · 측정 설계

“성공적으로 종료”와 “검증을 통과”를 분리한다

한눈에 요약

LibreDB agent는 planning, investigation, query-optimization, database-assessment, operations, data-analysis의 6 surface와 evidence-citing verifier를 가집니다.

한 cell은 한 모델·한 surface를 5회 연속 pass해야 잠기며, 6개 cell을 한 sitting에서 읽는 row score를 사용합니다.

작은 모델의 능력을 보려면 database 크기보다 loop·tool contract·verifier를 고정해야 한다는 설계입니다.

실험은 Apple M5 Max 18-core/64GB, Ollama 0.33.0, Bun 1.4.2, SQLite employee/department/salary schema, 기본 90초 turn limit에서 수행됐습니다. “succeeded”는 process exit일 뿐 pass가 아니며, 2,204 model-stopped 중 1,405가 unanswered였습니다.

02Corpus · Taxonomy

tool을 호출한 뒤 전달에 실패한 run이 가장 큰 손실 클래스다

한눈에 요약

8,199 run 중 4,951은 모델에 귀속됐고, 14,008 tool call이 거부됐습니다. 6 surface에서 data-analysis pass rate는 38.8%, planning은 83.2%였습니다.

2,100 model-attributed agent-mode loss의 clock-first 분류는 transport 36.2%, clock 25.8%, verification 20.7%, capability 17.3%입니다.

“작은 모델은 아무것도 못 한다”는 capability threshold 가설과 달리, 많은 실패는 tool을 실제로 사용한 뒤 deliverable을 통과시키지 못한 transport였습니다.

clock과 capability 정의는 일부 겹치므로 capability-first로 순서를 바꾸면 clock 18.8%, capability 24.3%가 됩니다. 그래도 transport가 가장 크고, tool invocation이 있었던 손실이 1,590/2,100(75.7%)입니다.

03Transport · 실패 모양

정답에 가까운 값이 schema의 다른 칸에 들어가거나 text channel에 남는다

한눈에 요약

캡처한 69 stopping turn 중 27개가 실행되지 않은 tool call을 assistant text에 완전한 JSON처럼 남겼고, 18개는 report tool이었습니다.

compose_report refusal만 9,707건(전체 69.3%)이며, displaced field·near-miss key·sibling field 제거 지시가 반복됐습니다.

production ledger가 model arguments를 저장하지 않았기 때문에 열흘 동안 “필드가 없다”만 보였고, 임시 argument dump를 추가한 뒤 기계적 모양이 드러났습니다.

대표 사례는 statement가 change enum에 들어가고 rationale가 reason으로 오며 evidence 한 항목이 배열 대신 객체로 온 경우입니다. 또 present_answer에는 artifact만, compose_report에는 presentation이 들어갔는데 서버가 한 도구에는 필드를 요구하고 sibling 도구에서는 제거하라고 해 deliverable을 잃었습니다.

04Intervention · 개입 결과

모델을 바꾸지 않고 서버의 tolerant parser를 고쳤다

한눈에 요약

다섯 서버 개입은 text-channel naming 인식, SQL로 kind 추론, displaced field/list 정규화, near-miss rename, sibling field의 올바른 목적지 안내였습니다.

같은 hardware·prompt·task에서 granite4.2:3b 21→28/30, llama3.1:8b 10→24/30, cogito 0→21/30 등 개선을 관찰했습니다.

이 수치는 “서버 수정이 모든 실패를 해결한다”는 ablation이 아니라, production 결함을 고친 뒤의 field observation입니다.

intervention 1만 단독으로 본 네 cell은 +1,0,0,−1로 변동 범위였고, 세 모델은 이전 측정이 여러 날·설정의 union이어서 row protocol과 완전히 비교할 수 없습니다. 따라서 개선폭을 인과 효과로 과장하면 안 됩니다.

05Validity · 결론

context 길이·swap 압력도 모델 실패처럼 보인다

한눈에 요약

7.1GB 모델이 262,144-token context로 64GB 중 51GB를 점유했고, 같은 3B planning cell은 uncapped 0/5에서 32,768 cap 후 5/5가 됐습니다.

단일 Mac·SQLite schema·불균등 sample·3,248 unattributed run 때문에 결과를 일반 법칙으로 확장할 수 없습니다.

모델 benchmark를 운영할 때 서버 계약과 시스템 자원도 독립 변수로 기록해야 한다는 것이 가장 실용적인 결론입니다.

저자들은 context cap, swap/pageout, port restart, row scoring, argument capture를 명시합니다. 실제 운영에서는 모델별 tool-call parse율, refusal reason, context length, resident memory, swap, timeout, verifier pass를 함께 수집해야 합니다. 코퍼스·scorer·verifier는 GitHub와 dataset DOI로 공개돼 있습니다.

생활 속 비유 · 작은 예 · 논문 대응

비유: 자동차 성능을 비교하면서 한 차에만 무거운 짐을 싣고 “엔진이 약하다”고 결론 내리면 안 됩니다. 작은 예: context를 무제한으로 두면 모델은 메모리 부족으로 timeout하지만 로그에는 아무 tool도 안 쓴 것처럼 보입니다. 논문 대응: cap·swap·server 상태를 통제하지 않으면 capability 결과를 오해할 수 있습니다.
