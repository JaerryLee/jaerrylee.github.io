01Problem · 평가 단위

함수 전체를 점수화하면 실제 수정과 주변 문맥을 구분하지 못한다

한눈에 요약

Big-Vul의 실제 C/C++ 취약 함수 203개, 7개 CWE를 사용해 CodeGen-350M, DeepSeek-Coder 1.3B/6.7B를 zero/few/chain-of-thought로 평가했습니다.

compile rate는 pass@1의 값싼 대리 지표이고 CodeBLEU는 reference similarity지만, 둘 다 edit가 아니라 whole function을 봅니다.

논문은 “모델이 더 좋은 수정문을 썼는가?”와 “출력이 컴파일되는가?”를 같은 질문으로 취급하면 안 된다고 주장합니다.

비유: 틀린 문장 한 단어를 고친 시험에서 답안지 전체와 원본의 닮은 정도만 점수로 매기면 아무것도 안 고친 답안이 유리합니다. 작은 예: 취약 함수 그대로 복사한 no-op이 사람 수정과 가장 비슷하게 보입니다. 논문 대응: edit 영역만 별도로 봐야 한다는 출발점입니다.

02Method · 데이터·하니스

컴파일 여부를 측정하되 프로젝트 문맥과 전처리 아티팩트를 분리한다

한눈에 요약

203개 함수는 CWE-119/125/189/20/200/264/399 각 29개입니다. 70개 subset은 예산·플래그 ablation에 사용했습니다.

stub-injection harness가 헤더·타입·함수·필드 누락을 진단해 임시 선언을 추가하고 gcc/g++ -fsyntax-only를 재시도합니다.

이 하니스는 격리된 함수도 최대한 공정하게 컴파일하려는 장치지만, 프로젝트 수준 의미나 exploit 제거를 증명하지는 않습니다.

03Results · 지표 실패

컴파일률은 개선에 둔감하고 환경에 민감하며 최적화하면 게임된다

한눈에 요약

256→512 token 예산은 잘린 출력과 CodeBLEU를 개선했지만 compile rate는 거의 변하지 않았습니다.

실패의 약 64%는 모델이 아니라 missing project context, harness/toolchain, Big-Vul return-type artifact였습니다.

같은 모델 출력을 compiler flag만 바꿔도 compile rate가 1.8–2.7배 달라졌습니다. 따라서 정확한 toolchain을 적지 않은 수치는 재현할 수 없습니다.

04Results · 게임 가능성

whole-function CodeBLEU는 no-op을, compile feedback은 삭제를 보상한다

한눈에 요약

취약 함수 그대로 복사한 no-op은 CodeBLEU 0.775로 모든 모델보다 높았습니다.

compiler feedback loop는 instruction DeepSeek-1.3B compile rate를 3.9%에서 9.4%로 올렸지만 #if 0, bare declaration, placeholder 같은 비복구 patch가 나타났습니다.

05Implications · 실무

실행 oracle이 우선이고, proxy는 하니스와 degenerate baseline을 함께 공개해야 한다

한눈에 요약

diff_F1은 개발자 수정과 겹치는 edit 영역을 보지만 repair quality metric이 아닙니다. 사람 평가·실행·exploit 검증과의 상관은 검증되지 않았습니다.

논문은 exact compiler flags, no-op baseline, degenerate patch baseline, failure taxonomy를 함께 보고하라고 권고합니다.

취약점 복구 파이프라인은 “컴파일됨”에서 멈추지 말고 프로젝트 테스트·정적분석·실행 또는 exploit 재현을 단계적으로 붙여야 합니다.

데이터 누수와 Big-Vul 중복·전처리 오류도 기록해야 합니다. 203개가 7개 CWE에 집중되어 있고, 350M–6.7B 모델 비교도 동일한 base 모델 조건이므로 다른 언어·프로젝트·instruction 모델에 곧바로 일반화할 수 없습니다.
