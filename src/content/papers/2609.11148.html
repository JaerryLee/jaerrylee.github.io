01Motivation · 동기

“파이프라인 미로”가 만드는 운영 병목

한눈에 요약

수십 PB의 웹·코드·PDF 데이터가 임시 테이블과 수동 작업으로 흩어지면 기능 추가, 실패 복구, 계보 추적이 모두 어려워진다. OmniTable은 문제를 계산량보다 조정 비용의 문제로 본다.

기존 레이크하우스가 ACID와 스키마 진화를 제공해도 LLM 데이터 준비의 반복 단위는 테이블보다 기능 컬럼이다. 논문은 이질적 원천, PB 규모, 빠른 기능 backfill, 재현 가능한 계보라는 네 요구를 제시한다.

초등학생도 이해하는 설명

여러 상자에 재료를 나눠 넣고 요리법을 매번 다시 찾는 상황이다. OmniTable은 재료 목록과 요리법 연결을 한 곳에서 관리한다. 실제 시스템은 수십 PB 데이터라는 점이 비유의 한계다.

02Architecture · 구조

논리적 통합, 물리적 분리

한눈에 요약

사용자는 하나의 논리 와이드 테이블에서 행을 등록하고 컬럼 기능을 선언한다. 카탈로그는 내부에서 물리 테이블·행 파티션·컬럼 샤드로 나누어도 같은 논리 계약을 유지한다.

_ai_unique_id_는 행·단계·기능을 연결하고, _ai_append_name_은 배치·출처·버전을 표시한다. Catalog, Feature Engine, Exploration, Governance 서비스가 메타데이터를 공유한다.

초등학생도 이해하는 설명

한 장의 표처럼 보이지만 자주 쓰는 칸은 가까운 서랍, 드문 칸은 보조 서랍에 둔다. 사용자는 서랍 위치를 몰라도 같은 표를 조회한다.

03Execution · 실행

기능 생명주기와 자율 거버넌스

한눈에 요약

기능을 선언하면 의존성 해결, 실행 계획, 연산자 융합, 계보 기록이 자동으로 수행된다. 작은 파일·열 한도·접근 패턴이 변하면 백그라운드에서 물리 레이아웃을 바꾼다.

공통 입력 기능은 한 번의 스캔으로 융합하고, 문제가 있는 레코드는 오류 테이블로 격리하며, CPU/GPU 라우팅과 배치 파라미터를 자동 조정한다. 탐색은 ID 인덱스·OLAP·materialized view로 분업한다.

초등학생도 이해하는 설명

도서관에서 책 번호 색인, 주제별 통계실, 자주 묻는 목록을 나눠 쓰는 것과 같다. 모든 질문에 한 방법을 강요하지 않고 시스템이 경로를 고른다.

04Evaluation · 평가

35PB 운영 환경의 결과

한눈에 요약

실제 배포 환경에서 전체 SFT 큐레이션은 약 14일에서 2.5일로 줄었다. PB 규모 처리량, 레코드 단위 장애 격리, 연산자 융합, 적응형 튜닝이 각각 다른 병목을 줄였다.

05Lessons · 교훈

운영 습관과 적용 경계

한눈에 요약

저자들은 UDF 단위 격리와 지속적 레이아웃 관리가 선택 기능이 아니라 운영 조건이라고 결론낸다. 시스템은 Iceberg·Delta를 대체하기보다 그 위에서 기능 DAG·계보·실행을 관리하는 계층이다.

작은 파일 누적과 열 폭증은 몇 주 안에 성능을 무너뜨릴 수 있다. SQL을 버리게 만드는 도구는 채택되지 않으므로 논리 표 인터페이스를 유지했다.

초등학생도 이해하는 설명

새 도구가 좋아도 익숙한 SQL을 버려야 하면 쓰지 않는다. 사용자는 표를 계속 조회하고 저장 정리는 시스템이 뒤에서 담당한다. 논문의 수치는 특정 생산 환경의 결과다.
