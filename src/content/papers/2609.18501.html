01Problem · 분산 DB에서 테스트가 놓치는 것

같은 SQL도 데이터 분포에 따라 전혀 다른 실행이 된다

한눈에 요약

중앙 DB용 SQL 생성기는 분산 DB의 shard routing, reference table, co-located join 조건을 충분히 탐색하지 못할 수 있습니다.

따라서 테스트는 SQL 문법 복잡성뿐 아니라 테이블 간 분포 관계와 실제 실행 가능성을 함께 고려해야 합니다.

DDBMS에서는 스키마만으로 데이터 위치가 정해지지 않습니다. 분포 전략도 query plan과 최적화 경로를 바꿉니다.

분산 테이블의 데이터가 한 shard로 제한되는지, 전체 shard에 퍼지는지, 다른 테이블과 함께 배치되는지에 따라 query routing·통신·join 전략이 달라집니다. 분포를 무시한 테스트는 실행이 거부되거나, 관심 있는 최적화 경로를 아예 자극하지 못할 수 있습니다.

02DAT Method · 테스트 데이터와 query mutation

스키마×분포 행렬과 이력 피드백으로 유효한 분산 경로를 탐색한다

한눈에 요약

SDM은 논리 스키마와 분포 전략 조합을 체계적으로 만듭니다.

DAT는 테이블 대체·predicate injection·join alignment로 query를 바꾸고, 과거 실행 가능성을 사용해 비생산적인 변형을 덜 시도합니다.

핵심은 SQL을 많이 만들어내는 것보다, 분산 DB가 실행하고 관심 있는 distributed path에 도달하는 테스트를 더 자주 만드는 것입니다.

SDM(Schema–Distribution Matrix)은 열 방향으로 유사 스키마 테이블을 교체하고, 행 방향으로 동일 분포 조건이 맞는 테이블을 묶어 쿼리 제약을 만족시키는 탐색 공간입니다. DAT의 변형 μ=(ρ,Δ)는 기본 쿼리의 table instance를 분포가 다른 호환 테이블로 바꾸고, 분산 전략을 겨냥하는 query transform을 더합니다.

4개 시스템마다 4–9개 schema와 4–6개 분포 전략을 가진 SDM을 생성하고, 표마다 40–120행을 채웁니다. 1,000개 query마다 SDM을 다시 만들며 query당 최대 10회 변형합니다. 실행 가능성은 “지원 안 됨”을 영구 증명하지 않고, feature path의 관측된 성공률로 추정합니다.

설계가 바꾸는 질문

랜덤 테스트가 “어떤 SQL을 쓸까?”라면 DAT는 “어떤 분포 조건을 붙이면 어떤 분산 실행 최적화가 발동할까?”를 먼저 묻습니다.

03Evaluation · 버그 발견과 실행 가능성

31개 신규 버그를 보고하고, 24시간 비교에서도 가장 많이 찾았다

한눈에 요약

전체 캠페인에서 31개 bug를 보고했고 28개가 분산 query 처리·최적화 관련이었습니다. 작성 시점 21개가 확인, 15개가 수정됐습니다.

별도 24시간 비교에서는 DistRanger가 16개(분산 관련 13개)를 찾아 SQLancer 0개와 EET 6개를 앞섰습니다.

한계와 남은 범위 Scope and limitations

DistRanger의 oracle은 현재 centralized/distributed 실행 결과 비교와 crash·error·timeout 등의 명확한 신호를 중심으로 합니다. 논문은 window 함수의 일부 형태나 설정 조합 등 아직 다루지 않는 버그 영역이 있다고 밝힙니다. DDBMS가 명시적이고 제어 가능한 분포 전략을 제공해야 하며, mutation 및 최적화 계측은 shard routing과 co-located join을 중심으로 구현되었습니다. 24시간 비교 및 전체 캠페인은 테스트 버전과 생성 파라미터가 정한 탐색공간에서 얻은 결과이지, 제품 전체 안정성의 완전한 증명은 아닙니다.

실무 요점

분산 DB 회귀 테스트에는 SQL text만 저장하지 말고, 사용한 schema·distribution matrix·optimization path·실행 가능 여부·시스템 버전을 함께 남겨야 재현과 원인 분리가 가능합니다.

핵심 용어 정리

분포 전략Distribution strategy

행이 어떤 shard에 놓이거나 복제되는지를 정하는 정책.

shard routingShard routing

조건으로 관련 shard만 골라 query를 보내는 최적화.

co-located joinCo-located join

join key가 같은 위치에 있는 데이터를 네트워크 이동 없이 결합하는 실행.

SDMSchema–Distribution Matrix

논리 schema와 분포 전략의 조합을 조직한 테스트 구성.

feature pathQuery feature path

false positiveFilter false positive

＋One-page Summary · 한 장 정리

이 논문을 한 장으로

01
DDBMS의 query behavior는 SQL semantics뿐 아니라 테이블 배치와 분포 전략에도 좌우된다.
02
SDM으로 스키마·분포 조합을 만들고 mutation으로 shard routing·co-location 조건을 적극 탐색한다.
03
실행 가능성 history는 유효 query 비율을 높이지만 threshold가 높으면 합법 경로도 걸러낼 수 있다.
04
31개 신규 bug(28개 분산 관련)는 전체 캠페인, 16개 bug(13개 분산 관련)는 별도 24시간 비교의 수치다.
05
DistRanger는 Vitess에서 641MB 수준을 사용했으며 그 대부분은 feature path history였다.
