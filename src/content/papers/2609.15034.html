01Problem · 문제

CPU용 디코더를 GPU에 옮기면 메모리 시스템이 병목이 된다

한눈에 요약

기존 Deflate·LZ4·Snappy 디코더는 CPU의 순차 실행을 전제로 한다. GPU에서는 사전 조회가 흩어지고 출력 쓰기가 짧아져, 연산 유닛이 아니라 메모리 접근이 속도를 제한한다.

저장 데이터는 전송량을 줄이기 위해 압축되어 있지만, 분석 직전에 복호화해야 한다. Blackwell GPU의 Decompression Engine(DE)은 범용 압축을 하드웨어로 처리하지만, 논문은 고정 폭 토큰을 사용하는 FSST·OnPair 계열을 소프트웨어로 병렬 복호화하면 더 높은 처리량을 낼 수 있는지 묻는다.

초등학생도 이해하는 설명

압축을 풀 때 실이 한 가닥인 CPU 방식은 GPU에서 줄을 세운다. 여러 사람이 동시에 상자를 열려면 각자 어디에 물건을 놓을지 미리 알려줘야 한다.

02Design · 설계

FastPair는 조회·위치 계산·쓰기 세 단계를 다시 배치한다

한눈에 요약

FastPair는 코드에서 사전 주소를 바로 계산하고, prefix sum으로 출력 위치를 미리 정하며, 공유 메모리에서 모은 뒤 연속적인 16바이트 덩어리로 쓴다. 이 세 선택이 GPU의 비연속 읽기와 작은 쓰기를 완화한다.

OnPair의 CPU 루프는 코드→offset/length 표→토큰이라는 두 번의 의존 읽기를 한다. FastPair는 사전을 고정 stride의 low/high plane으로 나눠 주소 계산을 없애고, 배치마다 저장된 sidecar offset과 warp prefix sum으로 각 토큰의 목적지를 찾는다. 길이가 긴 토큰의 high plane 읽기는 큐에 넣어 emit 단계와 겹치며, 최종 출력은 head/body/tail로 나눠 정렬·coalesced 쓰기를 만든다.

GPU가 먼저 읽고, 위치를 계산하고, 마지막에 한꺼번에 쓴다. 장난감 블록을 각자 흩어 놓지 않고 조립대에서 모아 한 번에 옮기는 방식이다.

03Tuning · 튜닝

토큰 수와 사전 읽기 폭이 데이터별로 달라진다

한눈에 요약

기본 권장값은 K=6, H=1, B300에서 T=256·B=4다. 그러나 W=8 split read는 짧은 토큰이 많은 열에서, W=16은 긴 토큰이 많은 열에서 유리하다.

논문은 K를 키울수록 처리량이 증가하다가 레지스터 압박으로 감소하는 현상을 측정한다. W=8은 토큰의 40% 이상이 8바이트 이하일 때 유리하며, 60%를 넘는 토큰이 8바이트보다 길면 W=16을 권장한다. 공유 메모리에 사전을 올리면 전역 읽기는 줄지만 공유 메모리 bank conflict와 점유율 저하 때문에 OnPair-12에서 26%, FSST-12에서 54% 느려졌다.

04Evaluation · 평가

B300에서 DE보다 2.4–4.2배 빠르다

한눈에 요약

10개 실제 데이터 열에서 FastPair는 B300 기준 952–1,529 GB/s(OnPair-12), 814–1,620 GB/s(OnPair-16)를 기록했다. 최고치는 Loghub Windows의 1,620 GB/s로, DE의 650 GB/s보다 2.5배 높다.

논문은 다섯 GPU와 실제·합성 열을 대상으로 최소 100회 측정의 최솟값을 사용했다. FastPair는 실제 열에서 2.4–4.2배 DE를 앞섰지만 OnPair-16과 OnPair-12 중 하나가 모든 데이터에서 이기지는 않았다. HBM GPU에서는 L1 pipe가 약 99% 포화되는 반면 디바이스 메모리 대역폭은 24–60%만 사용되어, 다음 최적화 지점이 전역 메모리가 아니라 비효율적인 L1 접근임을 보여준다.

초등학생도 이해하는 설명

빠른 숫자 하나만 보면 안 된다. 어떤 열은 OnPair-16, 다른 열은 OnPair-12가 낫고, GPU의 어느 파이프가 찼는지까지 봐야 한다.

05Limits · 한계

L1 파이프와 데이터 분포가 최종 상한을 정한다

한눈에 요약

FastPair는 압축 형식 자체를 새로 만들기보다 FSST-family 입력과 GPU 구조를 맞춘 디코더다. 따라서 CPU·GPU 조합, 사전 크기, 토큰 분포가 바뀌면 이득도 달라진다.

사전 읽기와 공유 메모리 쓰기가 모두 L1 접근률을 소비하므로, 디바이스 메모리 대역폭이 남아 있어도 처리량이 오르지 않을 수 있다. 논문은 압축률을 사전·sidecar까지 포함한 실제 저장 형태로 정의하고, 더 넓은 코덱·다른 GPU·쿼리 연산과의 통합은 후속 과제로 남긴다.

한 줄 결론

GPU 데이터 엔진의 복호화는 압축률 경쟁이 아니라, 토큰 배치·오프셋·메모리 파이프를 함께 설계하는 문제다.

초등학생도 이해하는 설명

상자 개수만 줄인다고 배송이 빨라지지 않는다. 창고 통로가 막히지 않게 상자를 옮기는 순서도 설계해야 한다.
