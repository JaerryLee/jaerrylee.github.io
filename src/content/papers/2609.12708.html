01Study · 연구 설계 · 네 가지 품질 축

정답률만으로는 AI 코드의 품질을 설명할 수 없다

한눈에 요약

연구는 구조 복잡도, 통계적 자연스러움, 정적 결함, 보안 취약점을 분리해 비교한다.

Python·Java·C는 동적 스크립트·엔터프라이즈·시스템 언어의 서로 다른 위험을 대표한다.

각 human 함수의 docstring과 signature를 바탕으로 세 AI assistant가 구현을 만들고, 같은 함수쌍을 여러 분석기로 검사했다.

02Metrics · 측정 · 복잡도와 자연스러움

짧고 단순한 코드가 곧 유지보수하기 좋은 코드는 아니다

한눈에 요약

AI 함수는 평균적으로 더 짧고 branching이 적어 MI가 높아지지만, 이는 metric이 크기와 복잡도에 의존하기 때문이다.

n-gram cross-perplexity는 AI 코드가 서로 더 비슷한 템플릿을 공유하는지 본다.

연구는 identifier를 정규화한 뒤에도 남는 예측 가능성을 측정해 이름의 영향과 구조의 영향을 분리했다.

03Dataset · 데이터 · 생성 조건과 재현성

대규모 비교지만 하나의 생성 조건으로 일반화하지 않는다

한눈에 요약

Python·Java는 CodeSearchNet/HMCorp, C는 TheVault에서 가져왔고, docstring+signature 단일 prompt로 생성했다.

정적 분석은 기능적 정답·실행 의미를 측정하지 않으며, training-data contamination과 model heterogeneity도 한계다.

이 연구는 “AI 코드가 보편적으로 나쁘다”는 실험이 아니라, 정해진 언어·모델·프롬프트에서 non-functional quality profile이 어떻게 다른지 보는 연구다.

04Results · 결과 · 스타일·자연스러움

AI 코드는 더 압축되고 더 서로 비슷하다

한눈에 요약

AI 산출물은 human보다 함수 크기와 branch가 작고, n-gram 모델에서 자기끼리 더 잘 예측되는 스타일을 보인다.

OpenAI 계열이 human에 상대적으로 가깝고 DeepSeek-Coder가 가장 큰 구조·결함 차이를 보이며 Qwen은 중간에 놓인다.

자연스러움은 “좋다/나쁘다”가 아니라 저자 스타일의 통계적 규칙성이다. 이 지표는 AI 생성물 탐지와 반복 패턴 파악에는 유용하지만 correctness를 대신하지 않는다.

05Risk · 위험 · 결함과 보안

결함의 “양”보다 종류와 언어가 중요하다

한눈에 요약

human 코드는 성숙한 코드베이스의 복잡한 결함이, AI 코드는 unused parameter·boilerplate·unchecked return 같은 반복 결함이 더 눈에 띈다.

Python·Java에서 AI의 취약점이 더 많거나 심한 경우가 있지만, C에서는 human의 memory-safety 문제가 더 크다.

AI 코드를 하나의 저자로 취급하면 안 된다. 모델·언어마다 reviewer가 먼저 볼 위험 목록이 달라진다.

06Interpretation · 해석 · 무엇이 품질을 설명하는가

복잡도 하나로는 품질 격차를 설명하지 못한다

한눈에 요약

NLOC를 통제하면 대부분의 복잡도-결함 상관이 약해지고, 보안 결과는 구조 metric과 거의 무관하다.

자연스러움도 모델·언어에 따라 방향이 바뀌어 여러 분석 축을 함께 봐야 한다.

저자들은 CQBench를 공개해 analyzer가 잡는 issue-prone task를 재현 가능하게 평가한다. 다만 benchmark는 correctness·exploitability의 대체물이 아니다.

07Practice · 실무 · AI 코드 리뷰

AI 코드에는 다른 리뷰 순서가 필요하다

한눈에 요약

복잡도만 낮다고 통과시키지 말고 누락된 validation, edge case, unchecked return, hardcoded credential, debug artifact를 먼저 본다.

Python/Java는 injection·정보 노출·secure configuration, C는 memory safety·race·command injection을 언어별로 점검한다.

CQBench 같은 issue-prone benchmark를 CI 보조 지표로 쓰되, 실행 테스트·코드 리뷰·보안 분석을 대체하지 않는다.

실무 체크리스트

생성 코드 수용 전: (1) 입력 경계와 error path, (2) 외부 호출 반환값, (3) secret·credential, (4) 언어별 CWE, (5) 실제 테스트와 semantic contract를 확인한다.
