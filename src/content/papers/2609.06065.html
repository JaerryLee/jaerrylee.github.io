01Problem · 연결 대상의 이름이 지워짐

검색은 문장을 찾았는데, 그 문장이 누구 이야기인지 모른다

한눈에 요약

멀티홉 질문을 작은 질문으로 나눌 때 이전 단계에서 찾은 entity가 다음 질문에서 빠질 수 있다.

문서를 문장으로 나누면 대명사의 주인이 사라져, 정답 문장이 있어도 LLM이 근거를 연결하지 못한다.

이 논문은 검색 실패를 하나로 뭉뚱그리지 않고 lost-in-retrieval과 lost-in-generation이라는 두 끊김으로 나눈다.

예를 들어 “영화 My Left Foot의 주연 배우가 언제 아카데미상을 받았나?”는 먼저 배우가 Daniel Day-Lewis임을 찾고, 다음 질문에 그 이름을 넣어 수상 연도를 찾아야 한다. 그런데 두 번째 하위 질문이 “그 배우가 언제 받았나?”처럼 되면 dense retriever가 Daniel Day-Lewis 문서를 찾을 단서가 약해진다. 이것이 첫 번째 끊김이다.

두 번째는 검색 뒤에 생긴다. 원문에는 “Daniel Day-Lewis … He won … 1990”이라고 쓰였는데 sentence index가 “He won … 1990”만 돌려주면, 정답 문장 자체는 맞아도 He가 누구인지 알 수 없다. 저자들은 gold evidence와 distractor를 고정해 retriever를 아예 배제한 실험으로 이 손실을 분리했다.

초등학생도 이해하는 설명

친구 두 명이 각각 ‘그가 상을 받았어’라고 적은 쪽지를 떨어뜨렸다고 하자. 이름표가 없으면 쪽지를 주워도 누구 이야기인지 모른다. 이 논문은 질문 쪽에서도 이름을 지우지 않고, 정답 쪽지에도 다시 이름표를 붙인다.

02Method · 두 번의 entity 복구

다음 질문에 이름을 넘기고, 검색 문장 앞에도 이름을 붙인다

한눈에 요약

Two-way question decomposition은 비교 질문은 한 번에 둘로, 연결 질문은 답을 얻을 때마다 순차적으로 나눈다.

Subject-entity prefix는 각 문장 앞에 원문 문단의 대표 주어를 붙여 generation 단계의 문맥을 복원한다.

DER-RAG는 별도의 graph를 만들지 않는다. 기존 dense sentence retrieval과 reranker는 그대로 두고, 질문 흐름과 생성 입력에 entity 표지만 보강한다.

비교형 질문은 이미 두 대상이 질문 안에 명시돼 있으므로 한 번의 LLM 호출로 두 하위 질문을 병렬 생성한다. 비비교형 bridge 질문은 먼저 필요한 중간 entity를 묻고, 그 답을 다음 하위 질문의 명사로 직접 치환한다. 반복 깊이는 시작 전에 한 번 예측한다. corpus 쪽에서는 문단당 대표 subject entity 하나를 offline LLM 호출로 뽑아, 검색된 문장 앞에 문장ID = 주어 : 문장 형식으로 붙인다.

중요한 비범위

문장 embedding이나 index는 다시 만들지 않는다. prefix는 검색 점수 계산용 문장이 아니라 최종 LLM에 건네는 문장에 붙는다. 따라서 retrieval loss와 generation loss를 각각 다른 위치에서 고친다.

초등학생도 이해하는 설명

첫 번째 장치는 릴레이 선수가 다음 선수에게 이름표가 붙은 바통을 넘기는 일이다. 두 번째 장치는 답 쪽지마다 ‘이 쪽지는 다니엘 이야기’라고 머리표를 붙이는 일이다. 도서관 자체를 새로 짓지는 않는다.

03Mechanics · routing과 prefix의 작동 조건

모든 질문을 순차 처리하지 않고, 비교 질문만 빠르게 갈라 보낸다

한눈에 요약

비교 질문과 bridge 질문의 의존 구조가 달라서 routing이 필요하다.

대표 주어 하나라는 단순한 메타데이터로 문장 단위 검색의 정밀도와 문단 문맥을 절충한다.

질문 유형 분류기는 명시된 두 대상의 직접 비교인지 확인한다. 비교형이면 두 하위 질문이 서로의 답을 기다리지 않아도 되지만, bridge형은 앞선 답이 다음 질문의 핵심 검색어이므로 순서가 필요하다. 이 분류 한 번과 깊이 예측 한 번 외에는 별도의 fine-tuning이 없다.

주어 추출은 원문 제목을 그대로 붙이는 것보다 문단 실제 중심 entity를 고르는 쪽을 택한다. 한 문단에서 주어 하나만 고르므로 query마다 최적의 세밀도를 찾는 기법은 아니다. 대신 5,927개 문단 처리 비용이 1.15달러, 111.4분이었다고 보고해 구축 부담을 명시한다.

초등학생도 이해하는 설명

‘철수와 영희 중 누가 키가 큰가?’는 두 사람 키를 동시에 찾으면 된다. 하지만 ‘영희가 읽은 책의 작가는 어디서 태어났나?’는 책 이름을 먼저 알아야 작가를 찾을 수 있다. 그래서 문제 모양에 따라 길을 두 개로 나눈다.

길찾기 앱에 거대한 새 지도를 추가하지 않고도, 매번 ‘지금 누구를 찾는 중인지’를 잊지 않게 메모했더니 많이 좋아졌다. 특히 여러 사람을 차례로 찾아야 하는 문제에서 효과가 컸지만 모든 시험에서 1등은 아니었다.

06Limits · 어디까지 믿을 것인가

가벼운 보강의 증거이지, 지식 그래프 검색의 대체 증거는 아니다

한눈에 요약

한 문단당 주어 하나, 시작 시 한 번 예측하는 hop 깊이, Wikipedia 기반 세 QA dataset이라는 범위가 있다.

관계 제약·전역 요약·개인화된 장기 기억이 필요한 문제는 이 실험이 다루지 않는다.

문단이 여러 중심 entity를 담으면 고정 subject 하나가 잘못된 문장에도 붙을 수 있다. query별로 어느 entity가 중요한지 바꾸지 않고, multi-hop 깊이 예측이 틀려도 실행 중 수정하지 않는다. 실험은 200문제씩의 비교적 작은 표본이며 domain 문서·시간 변화·권한·citation 추적을 포함하지 않는다.

도입하기 좋은 때 entity가 중간에 자주 사라질 때

  • 문장 단위 dense RAG
  • bridge형 multi-hop QA
  • 그래프 구축 비용을 피해야 할 때

추가 구조가 필요한 때 전역·관계 질의

  • 커뮤니티 전체 요약
  • 명시적 path·constraint 탐색
  • 지속적 agent memory와 갱신

이름표를 잘 붙이는 방법은 훌륭하지만, 이름표가 도시 전체 지도는 아니다. ‘이 문장이 누구 이야기냐’는 잘 고쳐도, ‘회사 전체에서 어떤 부서들이 같은 문제를 겪나’ 같은 큰 질문에는 다른 도구가 필요하다.

＋Retrieval Family · 검색 계열 1차 판별

GraphRAG가 아니라 entity-aware adaptive multi-hop RAG다

한눈에 요약

논문 자체가 ‘no graph construction’을 명시하며 dense sentence retrieval과 reranking을 사용한다.

HippoRAG는 baseline일 뿐, DER-RAG에는 PPR·passage node·associative memory가 없다.

community report · global/local search · DRIFT가 없으므로 Microsoft GraphRAG가 아니다. Personalized PageRank · passage node · associative memory도 없으므로 HippoRAG 계열도 아니다. HNSW · Vamana · nearest-neighbor graph를 방법의 핵심으로 다루지도 않는다. 가장 정확한 분류는 기존 dense RAG에 질문 routing·rewriting과 generation-time entity prefix를 더한 방법이다.

초등학생도 이해하는 설명

‘그래프 방법보다 잘했다’는 말과 ‘이 방법도 그래프다’는 말은 다르다. 이 논문은 그래프 길을 만들지 않고, 기존 검색차에 이름을 잊지 않는 메모판을 달았다.

01
멀티홉 RAG의 entity 손실은 검색 전과 생성 전 두 곳에서 생긴다.
02
중간 답 entity를 다음 질문에 직접 넣고 검색 문장에 대표 주어를 붙인다.
03
그래프 구축·corpus 수정·fine-tuning 없이 강한 baseline과 경쟁했다.
04
한 문단 한 주어와 고정 깊이 예측은 실제 복잡한 corpus의 한계다.
05
정말 쉽게: 질문 바통과 답 쪽지에 모두 이름표를 붙이는 RAG다.
