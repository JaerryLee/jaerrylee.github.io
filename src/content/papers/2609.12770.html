01Problem · 문제 · 계약의 의미가 실행에서 무너진다

200·400·401이 있어도 API가 HTTP 의미를 지킨다는 보장은 없다

한눈에 요약

상태 코드는 숫자 목록이 아니라 클라이언트·서버 책임과 후속 행동을 전달하는 계약이다.

예를 들어 GET이 201을 반환하거나 401에 WWW-Authenticate가 없으면 도구와 클라이언트가 잘못 판단한다.

논문은 OpenAPI 문서와 실제 API 동작을 각각 관찰해 “문서가 말하는 것”과 “서버가 실제로 하는 것”의 차이를 잡는다.

핵심 문제

문서만 검사하면 구현 fault를 놓치고, 실행만 검사하면 “있어야 하지만 아직 관찰하지 못한 응답”을 오탐할 수 있다.

초등학생도 이해하는 설명

택배 상자의 라벨과 실제 내용물이 다르면 분류기가 틀린 곳으로 보낸다. 상태 코드는 라벨이자 약속이다.

02Approach · 접근 · SCOAS와 EvoMaster

정적 분석과 동적 분석은 서로 다른 빈틈을 채운다

한눈에 요약

SCOAS는 OAS의 path·method·response 문맥을 순회해 30개 규칙을 검사한다.

EvoMaster oracle은 실행 중 관찰 가능한 16개 규칙만 검사하고, 실제 재현 가능한 테스트를 만든다.

정적 검사는 빠르고 배포 전 단계에 넣기 쉽다. 동적 검사는 명세에 없던 실제 반환값까지 잡지만 부재를 증명할 수 없다.

규칙 그룹예시
성공/오류 의미GET에 201 금지, 구현된 endpoint에 501 금지
헤더/본문 조건401이면 WWW-Authenticate, 405이면 Allow
표준성비표준·미할당 status code 금지
HTTP 표준과 REST 원칙에서 만든 30개 사용 규칙의 핵심 묶음.

Static 명세를 넓게

  • 문서에 선언된 누락·부적합 응답 탐지
  • 실행 환경 없이 CI에 빠르게 삽입

Dynamic 실행을 깊게

  • 실제 반환 응답을 재현 가능한 테스트로 기록
  • 입력 생성과 커버리지에 의존
초등학생도 이해하는 설명

학교 규칙표를 읽는 검사관과 실제 운동장을 보는 감독관은 서로 다른 문제를 발견한다. 둘을 같이 써야 약속과 행동을 모두 본다.

03Evidence · 근거 · 분포와 정적 결과

오용은 예외가 아니라 반복되는 패턴이다

한눈에 요약

APIs.guru 2,529개 OAS에서 369,580개 응답과 127개 상태 코드를 분석했다.

200·400·401·403·404·500이 널리 쓰였지만 비표준 코드와 generic default도 반복됐다.

정적 분석은 30개 규칙을 적용해 명세 자체의 설계·문서 결함을 대규모로 세었다.

수치 해석

논문은 API 수가 아니라 “한 API에 한 번이라도 등장했는가”를 prevalence로 세어 큰 명세가 결과를 독점하지 않게 했다.

초등학생도 이해하는 설명

학교 전체에서 빨간 펜 표시를 세면 어떤 실수가 유행하는지 알 수 있다. 단, 같은 학생이 여러 번 틀린 횟수와 학생 수는 다른 지표다.

04Dynamic · 동적 · 실제 fault 재현

fuzzer가 만든 테스트는 규칙 위반을 재현 가능한 증거로 바꾼다

한눈에 요약

16개 규칙을 EvoMaster oracle로 구현했고 WFD 36개 API를 API당 1시간씩 10회 실행했다.

8개 fault 유형에서 수백 개의 실제 endpoint 위반을 찾았으며, GET→201·무본문→413·인증 없는 401 등의 테스트를 생성했다.

동적 검사는 존재하는 잘못을 확실히 보여주지만, 실행하지 못한 경로가 안전하다고 말할 수는 없다.

초등학생도 이해하는 설명

아이에게 “이 버튼은 빨간색이어야 해”라고 말하는 것과 실제로 눌러 보는 것은 다르다. 실행 테스트는 실제로 틀린 버튼을 눌러 확인한다.

05Limits · 한계 · CI 적용과 주의점

정적·동적 검사는 oracle의 한계를 드러내야 한다

한눈에 요약

동적 fuzzing은 실행되지 않은 경로의 부재를 증명하지 않는다.

프레임워크가 204/205 body를 조용히 제거하거나 library마다 비표준 status를 다르게 처리하는 문제도 있었다.

API quality gate에는 문서 검사와 실행 oracle을 함께 넣되, 각각이 보장하는 범위를 보고서에 명시해야 한다.

실무 도입 순서

① OpenAPI PR에서 SCOAS 실행 → ② nightly fuzzing에서 EvoMaster oracle 실행 → ③ 발견 fault를 재현 테스트로 고정 → ④ client SDK와 gateway의 status 해석을 함께 검증.

초등학생도 이해하는 설명

규칙표만 보고 “안전하다”고 결론 내리지 말고, 실제 운동장 테스트를 했는지와 못 한 구역을 함께 표시해야 한다.

dynamic oracle동적 oracle

prevalence유병률
