01Motivation · namespace 경계의 비용

논리적인 namespace 전환도 packet path에서는 반복 비용을 만든다

한눈에 요약

컨테이너는 network namespace로 격리되지만, host와 container 스택을 오갈 때 backlog queue를 중복 순회할 수 있습니다.

저자들은 짧은 연결 TCP_CRR 기준, namespace 제거 시 같은 host에서 31%, wire 통신에서 26% 처리율이 높아지는 차이를 먼저 측정했습니다.

패킷의 데이터가 물리적으로 다른 서버로 이동하지 않아도, Linux 네트워크 stack 경계는 추가 처리 경로를 끼워 넣을 수 있습니다.

host device가 받은 패킷은 대상 CPU의 per-CPU backlog에 들어가고, 이후 상위 network stack에서 처리됩니다. container의 veth로 넘어가면 namespace가 바뀐 뒤 다시 receive path와 backlog queue가 관여합니다. 보내는 방향도 veth의 host 측과 physical device 경계에서 유사 비용이 반복될 수 있습니다.

baseline은 Intel Xeon 3.1GHz CPU에서 네 구성(같은 host/다른 host × namespace 있음/없음)을 비교했습니다. 메모리나 Ethernet adapter capacity가 병목인 실험은 아니었다고 논문은 보고합니다.

02Design · netkit packet path

BPF가 정책을 적용한 뒤 namespace를 바꾸고 바로 전달한다

한눈에 요약

bpf_redirect_peer는 host에서 받은 패킷을 container stack으로 넘길 때 중복 backlog path를 생략합니다.

netkit pair는 container egress에서도 제어 plane이 안전하게 BPF를 붙일 수 있게 해, host network namespace 정보와 routing을 활용합니다.

설계의 중심은 데이터 전송 자체를 모두 우회하는 것이 아니라, 필요한 BPF 정책·route 처리 후 중복된 경로만 생략하는 것입니다.

첫 최적화는 physical device에서 host stack으로 들어온 패킷을 host tc-BPF에서 bpf_redirect_peer로 직접 container 상위 stack에 넘깁니다. 이때 host-side veth 송신 경로와 container-side backlog queue를 생략할 수 있습니다. 단, host netfilter 규칙은 redirect로 건너뛰므로 QoS·NAT·security policy를 BPF에서 처리해야 합니다.

netkit device는 transmit path에서 namespace 전환 직후 BPF를 실행할 수 있습니다. 컨테이너 안의 앱이 peer device 프로그램을 임의로 떼어 보안 정책을 우회하지 못하게 primary/peer 역할을 나눕니다. 기본값은 제어 plane이 프로그램을 붙이기 전 traffic drop으로 설정할 수 있습니다. netkit은 layer 3 모드가 기본이고 Ethernet semantics가 필요하면 layer 2로 쓸 수 있습니다.

보안·호환성 전제

host netfilter에서 처리하던 정책은 redirect에 의해 bypass될 수 있습니다. 따라서 BPF datapath가 security, QoS, NAT를 수행하고, host device에 달린 BPF 프로그램은 container 또는 physical device 쪽으로 옮기는 구성이 필요합니다.

설계는 모든 backlog queue를 제거한다고 주장하지 않습니다. 같은 host의 destination receive path에는 적어도 한 번의 queue traversal이 남습니다. sockmap으로 stack을 우회하는 대안은 일반 socket을 기대하는 컨테이너 앱의 full-stack 호환성 조건을 깹니다.

03Evaluation · throughput과 CPU

Cilium 환경에서 container 성능을 process 간 통신 수준까지 끌어올린다

한눈에 요약

TCP_RR에서 netkit은 same-node 처리율을 34%, wire를 건넌 처리율을 37% 높였습니다.

짧은 연결을 반복하는 TCP_CRR에서는 각각 32%, 26% 향상을 보였고, netkit 성능은 process-to-process host baseline과 거의 같았습니다.

측정은 2-node Kubernetes cluster에서 Cilium v1.19.5, Linux v6.8로 실행했습니다. 네트워크 stack의 패킷 처리량과 짧은 연결 성립 속도를 분리해 봅니다.

TCP_RR은 작은 패킷의 request-response rate로 latency 영향을 간접 측정하고, TCP_CRR은 짧은 TCP 연결을 얼마나 많이 성립시키는지 봅니다. Cilium은 native routing과 BPF masquerading·bandwidth manager·kube-proxy replacement를 사용하며, host netfilter rules는 제거했습니다.

성능 차이의 일부는 netkit이 더 적은 host netfilter/connection-tracking 경로를 지나기 때문입니다. flamegraph에서 보이는 BPF 프로그램 비용과 생략되는 처리 경로는 실험 오차 범위 안에서 해석됩니다. 구현 변경량은 새로운 redirect helper 78 lines, netkit kernel device 1,048 lines, Cilium helper 지원 49 lines 및 device-pair 지원 463 lines로 보고됐습니다.

읽어야 할 결과

이 결과는 throughput 숫자뿐 아니라 경로에서 빠진 보안·연결추적 비용도 포함합니다. 운영에 적용하려면 기존 host netfilter가 담당한 정책을 어디서 보장할지 함께 설계해야 합니다.

04Scope · 구현 조건과 남은 제약

빠른 경로는 netfilter·XDP·호환성 경계를 명시한다

한눈에 요약

netkit은 Linux kernel과 Cilium에 구현됐으며, 현재 시험 구성은 2-node cluster와 한 종류의 CPU hardware입니다.

host netfilter에 의존하는 정책은 redirect 경로에서 누락될 수 있고, destination backlog queue는 남습니다.

시스템 최적화는 어디를 건너뛰었는지, 그 자리를 누가 책임지는지까지가 기능 계약입니다.

netkit은 XDP를 지원하지 않습니다. 논문은 GRO로 합쳐진 packet을 기준으로 BPF 처리를 줄이려는 설계와, 일반 IPv4/IPv6 socket을 사용하는 app의 full stack 호환성을 이유로 설명합니다. device pair의 BPF 관리 주체는 host control plane이며, 컨테이너 앱은 peer device 프로그램을 직접 관리할 수 없습니다.

실험 결과는 3.1GHz CPU, Linux 6.8, LLVM 19.1.7로 빌드한 eBPF, Cilium 1.19.5의 2-node Kubernetes cluster에 조건부입니다. 하드웨어·CNI 구성·정책 배치가 달라지면 같은 향상 폭을 기대할 수 있다고 일반화할 수 없습니다. 이 논문은 eBPF’26 워크숍 논문으로 표기되어 있으며 행사 일정은 2026년 9월 29일–10월 2일로, 실행 날짜 기준 아직 개최 전입니다.

운영 검토 목록

netkit 도입 전 host netfilter 의존 규칙, BPF QoS/NAT/security 책임자, XDP 요구 여부, destination backlog의 잔여 비용을 점검해야 합니다. 본문의 성능값만 보고 host networking 정책을 우회하면 안 됩니다.

＋Glossary · 핵심 용어

핵심 용어 정리

network namespaceLinux network namespace

프로세스들이 격리된 network device·route·rule 상태를 공유하는 논리 경계.

backlog queuePer-CPU backlog

수신 패킷을 대상 CPU에서 이후 network stack으로 넘기는 대기열.

netkit pairPrimary / peer device

host control plane이 컨테이너 양측 BPF 프로그램을 관리하는 Linux 가상 network device 쌍.

bpf_redirect_peerBPF redirect helper

host tc-BPF에서 다른 namespace의 peer network stack으로 packet을 전달하는 helper.

TCP_RR / TCP_CRRnetperf benchmarks

request-response rate와 짧은 연결 성립 처리량을 각각 측정하는 benchmark.

GROGeneric Receive Offload

수신 packet을 상위 stack으로 올리기 전에 합쳐 처리 부담을 낮추는 Linux 기능.

이 논문을 한 장으로

01
network namespace 전환은 논리 경계이지만 Linux receive path에서는 backlog 순회가 반복될 수 있다.
02
netkit은 host tc-BPF redirect와 새 device pair로 중복 경로를 줄이며, 모든 queue를 제거하지는 않는다.
03
2-node Cilium benchmark에서 TCP_RR +34%/+37%, TCP_CRR +32%/+26% 향상을 보고했다.
04

05
단일 CPU hardware와 고정 kernel/Cilium 버전 결과를 다른 CNI·정책 구성에 그대로 일반화하면 안 된다.
