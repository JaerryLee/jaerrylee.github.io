01Problem · 왜 모델별 품질까지 라우팅에 넣나

가장 가까운 pod가 항상 가장 적합한 pod는 아니다

한눈에 요약

edge pod는 요청자와 가까워 빠를 수 있지만 작은 모델을 써서 정확도가 낮을 수 있고, cloud pod는 모델이 정확해도 왕복 네트워크 지연이 큽니다. 기존 round-robin·proximity 방식은 이런 모델 품질과 자원 상태를 함께 반영하지 못합니다.

ASRB는 지연시간과 application-level 품질을 한 점수로 결합하고, node-local proxy들이 분산해서 선택합니다.

논문은 분류 요청을 MobileNet-V2(더 빠르고 정확도 낮음)와 ResNet-50(더 느리지만 정확도 높음) 중 어느 인스턴스로 보낼지 다룹니다.

서비스 인스턴스는 edge, telco/MEC, cloud node들에 놓이고, 같은 API를 제공해도 모델이 다를 수 있습니다. ASRB는 pod placement를 결정하지 않고 이미 배치된 pod 중 요청별 목적에 맞는 목적지를 선택합니다. 각 노드에 DaemonSet proxy를 둘 수 있어 중앙 load balancer 병목을 피하고, Kubernetes API informer를 통해 pod와 node 상태를 동기화합니다.

생활 속 비유 · 작은 예 · 논문 대응

비유: 가까운 병원이 항상 필요한 전문 진료를 제공하는 것은 아닙니다. 작은 예: 모바일 화면에서 빠른 응답이 우선이면 MobileNet, 놓치면 안 되는 분류라면 ResNet을 선택할 수 있습니다. 논문 대응: ASRB는 응답 지연과 모델 정확도 사이 우선순위를 요청별 λ로 표현합니다.

02Routing · 점수 기반 요청 선택

한 개 가중치 λ로 latency와 accuracy의 우선순위를 바꾼다

한눈에 요약

각 pod의 점수는 최근 RTT가 낮을수록, 모델 accuracy가 높을수록 커집니다. λ=1이면 latency만, λ=0이면 accuracy만 중시하고 λ=0.5면 둘을 같은 가중치로 합칩니다.

먼저 fit node의 기준 이상 pod를 찾고, 없으면 overloaded node, 그마저 없으면 선택적으로 unfit 또는 random fallback을 사용합니다.

점수식은 단순하지만 λ를 어디서 어떻게 정할지는 서비스 운영자의 정책으로 남겨 둡니다.

Sₚ = λ × (1 − min(Lₚ / 1000, 1)) + (1 − λ) × Aₚ. 여기서 Lₚ는 가장 최근 RTT(ms), Aₚ는 모델별 정확도 annotation입니다. 지연 점수는 1000ms에서 포화됩니다. 정확도는 ASRB가 실시간 측정하지 않으며, application provider가 사전에 metadata로 제공한다고 가정합니다. λ는 각 요청에 실려 들어와 빠른 응답과 높은 품질 중 무엇을 우선할지 나타냅니다.

router는 Ready pod만 후보에 넣고 node label과 cached latency를 읽어 점수를 계산합니다. 값이 없거나 오래됐을 때는 비동기 /echo 요청으로 측정을 갱신합니다. 노드 상태와 QoS threshold에 따라 후보를 좁힌 뒤 가장 높은 점수의 pod로 전달하고, 응답 RTT로 cache와 node label을 업데이트합니다. pod 수를 N이라 할 때 검색·정렬은 O(N)입니다.

λ = 1 빠른 응답 우선

  • latency 점수만 반영
  • 낮은 RTT edge pod를 더 많이 선택
  • 품질은 model annotation과 policy 범위로 제한

λ = 0 높은 품질 우선

  • accuracy metadata만 반영
  • 더 정확한 모델을 주로 선택
  • 느린 추론과 network delay를 감수할 수 있음
생활 속 비유 · 작은 예 · 논문 대응

비유: 배달 앱에서 도착시간과 식당 평점을 어느 쪽에 더 비중 둘지 조정합니다. 작은 예: λ=0.5에서는 점수가 높은 ResNet 쪽으로 더 많이 보내되 latency spike 때 MobileNet으로 이동할 수 있습니다. 논문 대응: 점수식의 λ는 latency와 accuracy의 운영상 가중치이며, ASRB는 λ를 자동 학습하지 않습니다.

03Monitoring · 노드별 적응형 관측

늘 같은 주기로 모두 재지 말고, 중요하거나 흔들리는 노드를 더 본다

한눈에 요약

수동 관측은 매 서비스 요청의 RTT를 업데이트하고, 능동 관측은 cache가 낡았거나 비어 있을 때 가벼운 /echo probe를 보냅니다. ASRB는 fit·overloaded node를 자주, unfit node를 드물게 측정하며 성능이 불안정한 노드는 더 촘촘히 살핍니다.

관측비를 줄이되 상태 변화 감지를 늦추지 않도록 하는 것이 주요 설계 목표입니다.

ASRB의 핵심은 요청마다 무거운 모델을 추론하는 대신, cache된 지연 측정과 간단한 점수 계산으로 hot path를 가볍게 유지하는 것입니다.

노드는 fit, unfit, overloaded label을 받습니다. fit/unfit은 latency와 model quality 합성 점수에, overloaded는 CPU/memory threshold에 근거합니다. 각 proxy가 label을 Kubernetes API에 반영해 공유 상태를 만들며, overloaded는 routing 후보에서 배제하지 않고 fit pod가 없을 때 fallback으로 쓸 수 있습니다.

요청이 적거나 latency가 오래된 pod에는 /echo active probe를 보냅니다. 실제 요청 RTT가 다시 들어오면 exponentially weighted moving average로 cache를 부드럽게 갱신합니다. 관측 주기 이후 cooldown을 두어 같은 서비스에 probe가 폭증하지 않게 합니다. overloaded node는 빠른 변화 탐지가 필요해 자주 갱신하고, fit node는 중간 빈도, unfit node는 회복 여부를 감지할 정도로만 낮은 빈도로 갱신합니다.

저자들은 이런 방식이 대규모 배치에서 유리할 것으로 기대하지만, 많은 proxy가 Kubernetes API에 label을 갱신할 때 control-plane 비용이 어떻게 증가하는지는 별도 연구가 필요하다고 명시합니다.

생활 속 비유 · 작은 예 · 논문 대응

비유: 모든 도로를 매초 순찰하는 대신, 자주 막히는 길은 자주 확인하고 거의 쓰지 않는 길은 가끔 확인합니다. 작은 예: 지금 요청이 몰리는 overloaded node는 짧은 간격으로, QoS 점수가 낮아 선택되지 않는 노드는 긴 간격으로 살핍니다. 논문 대응: ASRB는 node label과 성능 변동 정도로 Prometheus/K8s 관측 강도를 배분합니다.

04Evaluation · 테스트베드와 결과

혼잡·재부팅·노드 추가 상황에서 품질 우선순위와 관측비를 비교했다

한눈에 요약

k3s 기반 실험은 far-edge 5/10ms, near-edge 50ms, cloud 150ms RTT의 가상 노드로 이루어졌고 이미지 분류 요청 1,200개를 여섯 단계로 흘렸습니다. ASRB는 latency 모드에서 QEP 대비 평균 응답시간을 18.64ms 줄였고, 일부 관측 설정에서는 QEP보다 monitoring traffic을 73% 줄였습니다.

λ를 0.5로 바꾸면 정확도 높은 모델에 더 많이 보내는 대신 median latency가 커집니다. 이 결과는 소규모 testbed에서 얻은 것입니다.

비교 대상은 ASRB 여러 λ/monitoring 구성, QEdgeProxy(QEP), proxy-mity 두 설정, round-robin입니다.

실험은 local data center 안의 Ubuntu 22.04 virtual machine으로 far-edge, near-edge, cloud를 구성하고 Linux tc로 RTT를 제어했습니다. 총 1,200개 요청을 보낸 동안 T1 초기 topology, T2 새 노드 추가, T3 reboot·회복, T4 새 pod 배포, T5 overload, T6 overload 해제를 차례로 만들었습니다. T5에서는 far-edge Worker 3·4에 stress를 걸어 CPU를 85% 넘게 사용시켰습니다. 즉, 실제 지리적으로 떨어진 edge/cloud가 아니라 latency 차이를 모사한 testbed입니다.

ASRB λ=1은 latency 중심 비교에서 proxy-mity보다 평균 9.79ms, QEP보다 18.64ms 짧았습니다. phase-stratified bootstrap CI가 0을 포함하지 않고 95% 수준에서 유의하다고 보고합니다. λ=0.5일 때는 요청의 85.4%가 고정확도 인스턴스로 가며, λ=1은 7.5%, proxy-mity는 7.1%, QEP는 2.6%였습니다. 그 대가로 λ=0.5 median latency는 440ms가 됐습니다. 전체 실험 동안 transient failure는 ASRB 2건, QEP 36건으로 보고합니다.

생활 속 비유 · 작은 예 · 논문 대응

비유: 신호등을 모두 같은 초 단위로 확인하는 대신, 교통량이 바뀌는 교차로만 더 자주 확인합니다. 작은 예: ASRB의 15s/60s 설정은 관측 트래픽을 73% 줄였지만 평균 latency는 5.3% 늘었습니다. 논문 대응: 적응형 모니터링은 비용을 낮추되, 설정에 따라 latency·응답성의 절충을 남깁니다.

05Discussion · 해석과 운영상 한계

정책을 구성 가능한 라우터이지, λ까지 자동으로 정하는 시스템은 아니다

한눈에 요약

ASRB의 유용한 점은 latency·model quality·node load 정보를 하나의 Kubernetes-native router에 모으고, 관측 빈도까지 조절한 것입니다. 다만 정확도는 주어진 metadata를 신뢰하며, λ가 올바른지는 운영자나 별도 정책이 결정해야 합니다.

testbed의 traffic 절감률을 수천 노드 규모 운영에 그대로 일반화할 수는 없습니다.

ASRB는 request route score 계산과 runtime telemetry 수집을 경량 proxy에 결합합니다. 하지만 “서비스에 맞는 trade-off”를 알아서 학습하는 것은 논문의 범위 밖입니다.

latency는 실제 RTT로 갱신되지만 accuracy는 사전 annotation이라고 가정하고, λ는 request에 실려 오거나 provider가 정합니다. 저자들은 장기 SLO fulfillment로 λ를 조정할 수 있는 가능성을 언급하지만 이 논문에서는 구현·평가하지 않습니다. 또한 모든 측정이 local data center VM들로 구성된 한 testbed, image classification, MobileNet-V2와 ResNet-50 두 모델, 1,200개 요청에 한정됩니다.

실험에서 ASRB가 label을 갱신하려고 Kubernetes API에 보내는 PATCH 요청도 monitoring cost에 포함했습니다. 소규모 클러스터에서는 절대 비용이 제한적이지만, 중앙 control plane으로 많은 proxy가 동시에 label update를 보낼 때의 충돌·쓰기 부하·staleness는 더 연구해야 합니다. 논문은 code를 공개한다고 적었으며, source link는 원문에서 asrb-proxy repository로 연결합니다.

실무에서 먼저 확인할 것

model accuracy metadata의 출처와 갱신 주기, λ를 누가 설정·감사하는지, ready/overloaded label이 오래됐을 때의 fallback, probe가 서비스에 주는 부하, Prometheus/API cache의 지연, 수천 node에서 label write가 만드는 control-plane 부하를 실제 환경에서 시험해야 합니다.

생활 속 비유 · 작은 예 · 논문 대응

비유: 항공사에 빠른 경로와 안전 여유 중 무엇이 중요한지 정해 주지 않고 자동 운항이 스스로 목적을 추측하게 하지는 않습니다. 작은 예: 의료 분류와 사진 검색은 같은 latency–accuracy 우선순위를 쓰기 어렵습니다. 논문 대응: ASRB는 trade-off knob를 제공하지만 λ 결정과 accuracy metadata 책임은 provider에게 남깁니다.
