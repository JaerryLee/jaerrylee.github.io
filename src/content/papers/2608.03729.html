01Problem · 문제

문자열은 실체가 아니다

한눈에 요약

LLM이 내놓은 이름을 그대로 ID로 쓰면 같은 이름의 다른 대상은 합쳐지고, 같은 대상의 다른 이름은 중복된다. GPTKB 2.0은 외부 위키 ID 없이 생성 과정에서 이 두 문제를 함께 처리한다.

Munich라는 도시는 Munich라는 영화와 분리하고, Île-de-France와 Île-de-France region은 같은 ID로 합쳐야 한다.

각 엔티티는 고유 ID, 대표 라벨, 한 문장 설명, 별칭 집합을 가진다. 트리플도 표면 문자열이 아니라 엔티티·관계·클래스 ID로 연결된다.

02Pipeline · 구축 방법

출처 트리플과 설명을 두 차례 써서 엔티티를 비중복화한다

한눈에 요약

시드 엔티티에서 사실을 추출하고, 객체가 명명된 개체인지 판정한 뒤 기존 후보와 병합하거나 새 ID를 만든다. 첫 NED는 출처 트리플, 두 번째 NED는 생성된 설명을 문맥으로 사용한다.

두 번째 단계는 Faculty of Law처럼 같은 라벨을 수백 실체가 공유하는 고밀도 동음이의어를 겨냥한다.

완전 병렬 NED는 동시에 등장한 동의어가 서로를 후보로 보지 못해 중복을 만든다. 그래서 객체 라벨을 군집화하고 먼저 등장한 대표를 우선 처리하는 guarded parallelization을 쓴다. 같은 관계-객체 라벨이 50회 이상 같은 ID로 연결되면 캐시한다.

03Scale & cost · 규모

70일 동안 4,770만 API 호출로 3,845만 트리플을 만들었다

한눈에 요약

최종 KB에는 159만 엔티티, 20.8만 관계, 6.65만 클래스가 있다. 활성 구축 시간은 70일, 총 API 비용은 6,992달러였다.

표본 1,000개 기준으로 엔티티의 36.8%가 Wikidata에 없었다.

엔티티 객체는 기존 ID로 580만 번 병합되고 140만 개가 새로 생성됐다. 캐시는 120만 객체의 API 호출을 피했다. 50만 엔티티까지 평균 비용은 엔티티당 약 0.015달러에서 0.008달러 근처로 내려갔다.

04Evaluation · 품질

표본 평가에서 90%대 정확도를 보였지만 표본과 평가자 한계가 있다

한눈에 요약

동음이의 병합은 98%, 분할은 100%, 동의어 병합은 91%, 근접 후보 내 동의어 분할은 95%였다. 사람 평가에서 트리플 94.5%가 참, 엔티티 96%가 검증 가능으로 분류됐다.

가장 큰 비중복화 오류는 동의어를 잘못 병합한 9%였다.

동의어 분할은 각 엔티티의 라벨 임베딩 상위 20개만 검사했으므로 아주 다른 표면형 중복은 놓칠 수 있다. 사람 트리플 평가는 저자 한 명이 200개를, 다른 저자가 그중 100개를 재평가해 90% 일치했다. 자동 평가는 웹 검색 에이전트와 생성된 설명에 의존한다.

05Prompts & limits · 재현성과 한계

이 KB는 근거가 붙은 사실집이 아니라 모델 믿음의 물질화다

한눈에 요약

개별 트리플에는 출처나 프로비넌스가 없고, 모델 학습 시점의 오류·편향·낡은 지식을 그대로 물려받는다. 저자들도 GPTKB 2.0을 금본위 KB가 아니라 LLM의 사실적 믿음에 대한 근사치라고 규정한다.

규모가 커도 신뢰 근거와 최신성은 별개의 문제다.

36.8% Wikidata 신규 비율은 1,000개 표본 추정치이며, 그 신규 부분의 검증 가능 비율은 90.5%로 전체보다 낮다. 성별·지역 편향도 나타난다. 아래 프롬프트들은 구축 절차를 공개하지만 API 모델 스냅샷과 검색·평가 환경 변화까지 고정하지는 못한다.

올바른 사용법

GPTKB 2.0은 LLM이 무엇을 믿는지 분석하고 탐색하는 자원이다. 외부 근거가 없는 트리플을 사실 확인 데이터나 고위험 의사결정의 직접 근거로 쓰면 안 된다.
