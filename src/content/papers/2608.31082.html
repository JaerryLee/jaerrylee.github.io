01Problem · 반복해서 긴 문서를 여는 비용

정답은 짧은데, 찾느라 수십만 토큰을 다시 읽는다

한눈에 요약

여러 문서에 흩어진 사실을 조합하는 에이전트는 정확하지만, 같은 긴 문서를 반복해서 읽어 비용이 커진다.

저자들은 한 번 읽을 때 재사용할 사실까지 구조화해 두면 다음 질문이 훨씬 싸질 수 있다고 본다.

이 논문이 겨냥하는 것은 단순한 “관련 문단 하나 찾기”가 아니라, 여러 문서를 열어 중간 표를 만들고 다시 계산해야 하는 data reasoning이다.

예를 들어 “히치콕과 스코세이지 둘 다와 일한 배우는 누구인가?”라는 질문은 두 감독의 영화 목록, 각 영화의 출연진, 두 집합의 교집합을 차례로 구해야 한다. FanOutQA의 질문은 평균 일곱 문서를 가로지르며, 저자 환경에서 에이전트 한 질문이 최대 약 100만 토큰과 거의 1달러를 소비했다. 비용의 대부분은 답을 길게 쓰는 decode가 아니라 문서를 입력으로 다시 읽는 prefill에서 나온다.

초등학생도 이해하는 설명

두꺼운 백과사전에서 선수 키를 찾은 뒤, 다음 날 같은 선수의 생일을 찾으려고 책을 처음부터 또 펼친다고 생각해 보자. 이 논문은 첫날 책을 펼친 김에 “이 선수의 키·생일·팀”을 작은 카드에 적어 두자는 생각이다. 다만 카드에 무엇을 적을지는 앞으로 어떤 질문이 올지 완전히 모르기 때문에 에이전트가 추측한다.

02Method · 질의가 구조를 만든다

미리 전부 구조화하지 않고, 필요해서 연 문서만 조금 더 캐낸다

한눈에 요약

질문을 처리하다 어쩔 수 없이 문서를 열었을 때, 별도 cracking 하위 에이전트가 미래에 쓸 법한 개체·속성·관계를 함께 추출한다.

다음 질문은 이 구조화된 저장소를 먼저 보고, 없을 때만 원문으로 돌아간다.

핵심은 adaptive와 speculative다. 실제 질문이 어떤 문서와 관계가 중요한지 알려 주고, 현재 질문보다 조금 넓은 사실을 추측해서 저장한다.

각 저장 항목은 확장된 RDF 간선 c = <s, r, o, κ, u, ε>다. 여기서 s는 주어, r은 관계, o는 다른 개체 또는 값, κ는 단일값인지 완전한 목록인지, u는 단위, ε는 어느 문서의 어느 부분이 근거인지 뜻한다. 목록 관계는 일부만 저장하면 완전한 답으로 오해할 수 있어, 전체를 뽑았을 때만 재사용 가능하게 표시한다.

전통적인 GraphRAG처럼 말뭉치 전체를 먼저 그래프로 만드는 방식과 달리, 이 방법은 질의가 만든 “문서 열기”를 계기로 저장소를 조금씩 채운다. 정확히 같은 질문의 답만 저장하는 semantic cache보다도 넓다. 예를 들어 득점을 물은 질문이 선수 페이지를 열면 리바운드 같은 가까운 속성도 함께 저장할 수 있다.

핵심 정의

Context cracking은 현재 질문이 이미 지불한 문서 읽기 비용을 미래 질문을 위한 구조화 자산으로 바꾸는 것이다.

초등학생도 이해하는 설명

도서관의 모든 책을 미리 카드로 만들면 일이 너무 많다. 그래서 누군가 실제로 빌린 책만 카드로 만들고, 그 사람이 찾던 내용 주변의 정보도 몇 개 더 적는다. 자주 보는 책은 카드가 풍부해지고, 한 번도 안 보는 책에는 일을 쓰지 않는다.

03System · KV cache를 두 번 활용

답하는 길과 카드 쓰는 길을 같은 읽기 지점에서 갈라낸다

한눈에 요약

문서가 이미 모델 문맥에 들어온 순간 분기해, 답변 에이전트와 cracking 에이전트가 같은 prefix를 공유한다.

질의 시에는 문서별 catalogue에서 가능한 주어–관계를 먼저 보고, 필요한 구조가 없으면 안전하게 원문을 연다.

저자들은 두 종류의 locality를 이용한다. 관련 질문들이 같은 문서를 다시 찾는 semantic locality와, 이미 계산된 문서 prefix를 하위 에이전트가 재사용하는 inference locality다.

쓰기 단계에서 cracking은 답변 경로 밖에서 병렬로 실행되므로 현재 답을 늦추지 않도록 설계됐다. 4K 출력 토큰 예산 안에서 schema-constrained JSON을 만들고, 후처리가 숫자·단위·날짜를 정규화하며 근거가 있는 항목만 넣는다. 읽기 단계에서는 catalogue가 문서마다 저장된 주어·관계·cardinality를 보여 준다. 이름이 정확히 맞지 않아 저장 항목을 놓치는 문제를 줄이기 위한 장치다.

초등학생도 이해하는 설명

선생님이 책 한 쪽을 칠판에 띄웠을 때, 한 학생은 지금 질문의 답을 찾고 다른 학생은 다음에 쓸 요약 카드를 만든다. 화면을 두 번 불러오지 않고 같이 보는 셈이다. 다음 질문에서 카드에 답이 없으면 책을 다시 펴므로, 카드를 잘못 준비해도 바로 추측하지 않는다.

04Evaluation · 재사용이 있을 때의 절감

비용은 크게 줄었지만, 반복 질문을 인위적으로 만들어 준 실험이다

한눈에 요약

FanOutQA에서는 평균 질문 비용이 0.26달러에서 0.12달러로, 영화 사례에서는 0.81달러에서 0.27달러로 줄었다.

정확도 차이는 통계적으로 유의하지 않았지만, 실험은 각 평가 질문 전에 관련 질문을 한 번 실행해 저장소를 데운 조건이다.

평가는 Claude Haiku 4.5 기반 FanOutQA 에이전트와 히치콕 중심 사례 연구로 구성된다. FanOutQA 자체에는 문서 재방문성이 거의 없어, 저자들은 각 시험 질문마다 다른 속성을 묻는 관련 질문을 Claude Opus 5로 생성하고 사람이 확인했다.

FanOutQA prefill은 평균 189K에서 87K 토큰으로, 사례 연구는 565K에서 161K로 줄었다. 평균 비용은 각각 0.26→0.12달러, 0.81→0.27달러였다. FanOutQA LLM-judge 정확도는 43.0%에서 42.0%로 1%p 낮았고 p=0.39라 유의한 차이가 아니었다. 문자열 정확도는 76.1%에서 74.2%였다. 4K cracking decode는 질문당 12%의 추가 비용을 만들었고, 재사용이 없는 90번째 백분위 질문에서는 오히려 baseline보다 1.24배 비쌌다.

초등학생도 이해하는 설명

카드를 한 번도 다시 쓰지 않으면 카드 만드는 시간이 낭비다. 이 실험은 시험 문제를 풀기 전에 비슷한 연습 문제를 하나 풀게 해서 카드가 쓰일 기회를 만들었다. 그러므로 “모든 실제 서비스에서 53% 절약”이 아니라, 관련 질문이 반복되는 서비스에서 얼마나 절약될 수 있는지를 보여 준 결과다.

05Validity · 강점과 남은 질문

아이디어는 강하지만 장기·기업 환경의 증거는 아직 없다

한눈에 요약

질의가 구조 구축 우선순위를 정하고, 저장 결과가 모델 교체 뒤에도 남는다는 방향은 LLM-Wiki와 매우 가깝다.

다만 Wikipedia 기반 짧은 워크로드, 정적 말뭉치, 생성된 관련 질문으로 평가했으며 장기간의 실제 질의 로그와 저장 오류 누적은 시험하지 않았다.

가장 중요한 기여는 “모두 미리 컴파일”과 “매번 원문 재독” 사이에 사용량에 따라 자라는 구조라는 세 번째 선택지를 선명하게 만든 것이다.

현재 도구는 제한된 주어·관계 조회만 제공하며 SQL의 집계·조인·다단계 질의를 안전하게 노출하지 않는다. 문서 수정 시 오래된 cracked object를 어떻게 폐기하거나 갱신할지도 구현되지 않았다. 추출은 미래 필요를 추측하므로 틀린 카드나 쓸모없는 카드가 누적될 수 있고, 사적 기업 문서에서의 일반화도 검증되지 않았다. 저자 역시 실제 장기간 질의 이력을 담는 benchmark가 필요하다고 적는다.

강한 점 비용을 지식 자산으로 전환

  • 원문 fallback으로 현재 정확도를 보호
  • 근거 위치·단위·목록 완전성을 저장
  • KV cache와 영구 구조를 함께 활용

주의 재사용 가정에 민감

  • 생성된 관련 질문으로 저장소를 예열
  • 실제 장기 로그·동적 문서 미평가
  • 오류·중복·신선도 관리 미완성
초등학생도 이해하는 설명

자주 보는 책의 카드를 조금씩 쌓는 생각은 아주 실용적이다. 하지만 학교에서 만든 연습 카드가 회사의 계약서에서도 똑같이 잘 작동하는지는 아직 모른다. 카드가 오래돼 틀렸거나 같은 사람이 다른 이름으로 두 번 저장되는 문제도 앞으로 풀어야 한다.

따라서 질의 주도 구조화 저장소를 쓰는 agentic retrieval로 분류하는 것이 정확하다.

핵심 용어 정리

Prefill입력 읽기

모델이 질문과 긴 문서를 처음 읽어 내부 계산을 만드는 단계다.

KV cacheKey-Value Cache

이미 읽은 토큰의 중간 계산을 저장해 같은 prefix를 다시 계산하지 않게 하는 메모리다.

Cracked object구조화된 사실

주어·관계·값·단위·완전성·원문 근거를 묶어 저장한 재사용 항목이다.

Semantic locality의미적 지역성

관련된 질문들이 같은 문서와 비슷한 개체를 반복해서 찾는 현상이다.

Fallback원문 복귀
