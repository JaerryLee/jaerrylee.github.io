VAETKI Commerce에서는 상품 이미지와 대화형 요청으로 마케팅 배너를 생성·편집하는 기능의 백엔드를 개발했다. 담당 범위는 배너 생성·조회·리사이즈·편집 API와 비즈니스 로직, AI 서비스 연동, 비동기 작업, 실시간 결과 알림과 DEV·RC 배포였다.

AI 서비스 호출을 연결한 뒤에는 작업의 상태와 결과를 일관되게 유지하는 문제가 남았다. 생성이 오래 걸리는 동안 사용자는 기다리거나 다시 요청할 수 있고, 결과 저장과 크레딧 처리 중 일부만 실패할 수도 있다. 이 글에서는 그 경계에서 처리한 내용을 정리한다.

## 생성 요청과 결과 전달을 분리한다

배너 생성과 이미지 편집은 일반적인 데이터 조회보다 오래 걸린다. HTTP 요청 안에서 모든 처리를 기다리는 대신 API가 작업을 만들고 Celery worker가 실제 처리를 수행하도록 구성했다. Redis·Celery 기반 작업 처리와 상태 관리, Socket.IO 기반 결과 이벤트를 연결했다.

작업 ID는 진행 상황과 최종 결과를 묶는 기준이 된다. API가 요청을 받았다는 사실, worker가 실행 중이라는 사실, 사용자가 결과를 사용할 수 있다는 사실을 같은 상태로 취급하지 않도록 했다.

이미지 생성 외에도 리사이즈와 대화형 편집에 같은 문제가 있었다. 대상 배너와 variation, 편집할 객체와 작업 ID를 연결하고, 성공·실패 결과를 해당 작업의 상태로 전달해야 했다.

## 크레딧은 예약·확정·취소의 단계를 갖는다

비용이 발생하는 AI 작업에서는 요청을 받았다는 이유만으로 모든 처리가 끝난 것처럼 크레딧을 확정하기 어렵다. 반대로 결과가 생성된 뒤에도 사용량 처리를 끝내지 않으면 결과와 과금 상태가 어긋날 수 있다.

그래서 작업의 크레딧을 사전 예약하고, 처리 결과에 따라 확정 또는 취소하는 경로를 연결했다. 특히 이미지 편집 작업에서는 크레딧 트랜잭션 ID와 확정·취소 상태, 취소 실패 정보를 별도로 기록했다.

| 상황 | 처리에서 구분한 내용 |
| --- | --- |
| 예약 이후 생성·편집 실패 | 확정이 시작되기 전이면 예약 취소 시도 |
| 결과 처리 후 확정 성공 | 크레딧 확정 상태를 기록하고 성공 전달 |
| 확정 요청 도중 예외 | 실제 반영 여부가 불확실할 수 있어 단순 취소 경로와 분리 |
| 취소 요청도 실패 | 취소 실패 상태와 오류를 남겨 후속 확인 가능하게 처리 |

여기서 가장 중요한 판단은 **예외가 발생한 시점과 외부 처리의 실제 완료 여부를 구분하는 것**이었다. 확정 요청을 보냈는데 응답을 받지 못했다고 해서 확정되지 않았다고 단정할 수는 없다.

이미지 편집 작업에는 확정 요청을 시작했는지를 나타내는 상태를 두었다. 확정 시작 전의 실패에만 예약 취소를 시도하고, 그 이후의 예외는 다른 실패 경로로 남겼다. 다음은 그 판단만 표현한 의사코드다. 저장·알림·복구의 세부 코드를 재현한 예제는 아니다.

```text
예약 ID를 받아 저장한다
편집 결과를 처리한다

확정 시작 여부를 기록한다
크레딧 확정을 요청한다
확정 성공 상태를 저장한다
작업 성공을 전달한다

실패하면:
  예약이 있고 확정을 시작하기 전이면 취소를 시도한다
  취소도 실패하면 그 실패를 별도로 기록한다
  작업 실패를 전달한다

종료 시 작업 잠금을 해제한다
```

이 구조가 모든 분산 트랜잭션의 문제를 해결하는 것은 아니다. 다만 실패했다는 이유로 무조건 취소를 호출하는 흐름에서 벗어나, 실제로 어느 단계까지 진행됐는지를 남길 수 있다.

## 같은 결과를 동시에 편집하는 요청을 제어한다

대화형 편집은 이미 만들어진 결과를 바꾸는 작업이다. 같은 variation에 두 요청이 동시에 들어가면 두 작업이 서로 다른 시점의 결과를 기준으로 수정할 수 있다. 늦게 끝난 작업이 더 최근 요청의 결과를 덮는 상황도 고려해야 한다.

AI Chat 작업에서는 편집 대상에 대한 작업 잠금과 충돌 제어를 연결했다. worker의 성공 경로뿐 아니라 예외 경로에서도 잠금을 정리하도록 종료 처리를 두었다.

잠금은 동시 실행의 범위를 제어하는 수단이다. 외부 요청의 성공 여부나 저장된 결과의 버전을 대신 설명해 주지는 않는다. 따라서 작업 상태, 편집 대상과 결과 보존 처리를 함께 봐야 했다. 프로세스가 강제로 종료되는 상황까지 일반적인 `finally` 처리 하나로 해결됐다고 주장하지 않는다.

## 부분 실패가 기존 이미지를 없애지 않게 한다

배너 기능은 하나의 파일만 다루지 않는다. 원본·생성 결과·편집 이미지·썸네일처럼 서로 다른 결과가 연결돼 있다. 그중 하나의 후처리가 실패했다고 이전에 사용하던 결과까지 버리면 사용자가 복구할 수 있는 지점이 사라진다.

내가 개선한 부분은 이미지와 썸네일의 생성·저장 과정에서 부분 실패가 발생했을 때 기존 결과를 보존하는 흐름이다. 편집 결과와 썸네일 처리를 구분하고, 정상적으로 확보하지 못한 결과가 기존 참조를 무조건 대체하지 않도록 처리했다.

실패를 단순히 성공으로 숨기는 방식은 아니다. 작업 실패는 남기되 이전 결과를 계속 참조할 수 있어야 한다. **새 작업이 실패했다는 사실과 기존 결과가 유효하다는 사실은 동시에 성립할 수 있다.**

이 관점은 크레딧 처리에도 이어진다. 결과 파일, 작업 상태, 크레딧 상태는 연결돼 있지만 같은 하나의 값은 아니다. 각 상태가 어떤 시점에 바뀌었는지 추적할 수 있어야 실패를 설명할 수 있다.

## 구현과 배포에서 맡은 범위

배너 기능의 백엔드 API와 비즈니스 로직을 개발하고, 상품 이미지 업로드와 AI 이미지·텍스트 수정 서비스를 연결했다. DEV·RC 환경의 CI/CD와 배포 자동화도 맡았다. Live 배포는 별도 운영 팀이 담당했다.

이 경험에서 남기고 싶은 것은 특정 큐나 프레임워크를 사용했다는 사실보다, 오래 걸리는 AI 작업의 완료 기준을 나눴다는 점이다. 요청 접수, AI 처리, 결과 보존, 크레딧 반영과 사용자 알림이 각각 어느 상태인지 설명할 수 있어야 운영 가능한 기능이 된다.

현재 [LLM Ops에서 로그와 트레이스를 연결하는 일](/posts/llm-ops-opentelemetry/)도 같은 질문으로 이어진다. 오류가 났다는 사실에서 멈추지 않고, 무엇이 완료됐고 어느 단계가 불확실한지 찾아갈 수 있어야 한다.
