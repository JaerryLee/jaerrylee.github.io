LLM 서비스는 HTTP 200을 반환하면서도 틀린 근거를 제시하거나 잘못된 도구를 실행할 수 있다. 따라서 가용성과 지연뿐 아니라 **답변 품질과 행동의 적절성**까지 변경 전후에 비교해야 한다.

이 글은 학습 자료를 공식 문서와 논문에 대조해 정리한 운영 설계 노트다. 아래 절차와 예시는 제안하는 설계이며, 실제 구축 성과나 측정 결과를 뜻하지 않는다. 자료 확인 기준일은 2026년 9월 28일이다.

## LLMOps를 다섯 가지 질문으로 나누기

LLMOps의 범위는 자체 모델 학습부터 외부 모델 API를 사용하는 애플리케이션 운영까지 이어진다. 모든 팀이 사전학습을 직접 해야 하는 것은 아니다. Microsoft의 운영 가이드도 데이터 정리, 실험, 평가, 배포, 추론, 모니터링, 피드백을 연결된 활동으로 설명한다. [Microsoft LLMOps 가이드](https://learn.microsoft.com/en-us/ai/playbook/technology-guidance/generative-ai/mlops-in-openai/)

| 지식과 외부 행동은 어떻게 연결할까? | [프롬프트·RAG·에이전트](/posts/llmops-rag-agent-design/) |

로그·메트릭·트레이스를 연결하는 구현은 기존 [OpenTelemetry 글](/posts/llm-ops-opentelemetry/)에서 다룬다. 여기서는 그 관측 결과로 출시와 개선을 판단하는 과정에 집중한다.

## 배포 단위는 모델보다 크다

같은 모델도 프롬프트, 검색 인덱스, 도구 권한이 달라지면 다른 서비스가 된다. 모델 파일만 이전 버전으로 돌려서는 장애 이전의 동작을 복구하지 못할 수 있다. 다음과 같은 **릴리스 명세**를 하나의 변경 단위로 관리하는 방식을 제안한다.

```yaml
# 개념을 설명하기 위한 명세 예시이며 특정 도구의 설정 형식은 아니다.
release_id: support-assistant-r12
model_revision: model-checkpoint-42
tokenizer_revision: tokenizer-7
prompt_revision: prompt-18
retrieval_snapshot: knowledge-2026-09-28
embedding_revision: embedding-3
tool_policy_revision: tools-9
runtime_image_digest: sha256:<image-digest>
generation_config_revision: generation-4
evaluation_report: eval-run-126
rollback_release: support-assistant-r11
```

레지스트리는 산출물의 위치와 승인 상태를 관리하고, 계보(lineage)는 데이터·코드·실험·모델·평가 사이의 연결을 기록한다. 변경 가능한 `latest` 태그보다 실제 revision이나 digest가 재현에 유리하다. 외부 API처럼 내부 가중치를 고정할 수 없다면 제공자가 노출하는 모델 버전과 관측 가능한 변경 범위를 기록한다.

## 평가셋과 평가기를 함께 관리하기

개발 중 반복해서 보는 회귀셋과 최종 판단용 홀드아웃을 구분한다. 같은 질문의 문장만 바꾼 예제가 학습셋과 평가셋에 함께 들어가면 점수가 실제 일반화 능력을 과대평가할 수 있다. 사용자·원문 문서·시점 등 업무에 맞는 단위로 분리하고, 실패 사례를 추가할 때도 이 경계를 유지한다.

| 평가 대상 | 확인할 지표·증거 | 점수만으로 놓치는 것 |
| --- | --- | --- |
| 형식과 API 계약 | 파싱 성공, 스키마 적합성, 필수 필드 | 형식이 맞아도 값은 틀릴 수 있음 |
| 검색 | 정답 근거의 Recall@k, 순위, 접근 권한 | 문서를 찾았어도 답에 잘못 사용할 수 있음 |
| 생성 | 정답성, 질문 관련성, 근거 충실도 | 주어진 근거 자체가 오래됐을 수 있음 |
| 도구 실행 | 작업 성공, 인자 정확성, 중복 실행 여부 | 그럴듯한 답변이 실제 작업 성공은 아님 |
| 안전 | 정보 노출·권한 위반·공격 사례별 결과 | 관측된 실패 0건이 위험 0을 의미하지 않음 |

예를 들어 Ragas의 faithfulness는 답변의 주장이 **제공된 문맥에서 뒷받침되는지** 평가한다. 이는 현실의 사실 여부나 문서의 최신성을 보증하는 지표가 아니다. 지표 이름만 도입하지 말고 분모, 필요한 정답 데이터, 판정 방식을 함께 확인한다. [Ragas Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

LLM-as-a-Judge는 대량 평가를 도울 수 있지만 평가기 역시 오류를 낸다. MT-Bench 연구는 답변 위치, 장황함, 자기 선호 등의 편향을 분석했다. 운영에서는 judge 모델·프롬프트·루브릭을 고정하고, A/B 제시 순서를 바꿔 비교하며, 사람 판정과의 불일치 사례를 점검하는 것이 좋다. judge를 바꾸면 과거 점수와의 비교 가능성부터 다시 확인한다. [LLM-as-a-Judge 연구](https://arxiv.org/abs/2306.05685)

## 품질 게이트는 평균 점수보다 구체적이어야 한다

출시 기준은 평가를 실행하기 전에 정한다. 전체 평균이 올라도 특정 언어, 긴 문서, 권한 경계에서 회귀가 생길 수 있으므로 핵심 업무별 결과를 따로 본다. 비결정적인 생성은 반복 실행의 변동과 표본 수를 같이 보고한다.

예를 들어 다음 세 조건을 별도로 판정할 수 있다. 수치는 서비스 요구와 기준선으로 정해야 하므로 여기서는 임의의 합격선을 두지 않는다.

1. 중요한 업무의 성공률과 근거 충실도가 기준선 대비 허용 범위 안인가?
2. 권한 위반 같은 중대 실패가 발견되었고, 있다면 출시를 중단해야 하는가?
3. 실제 부하에서 지연·오류·비용 목표를 만족하는가?

측정하는 지표가 SLI, 그 지표의 목표가 SLO이며, SLA는 목표 미달 시의 결과를 포함하는 서비스 합의다. 예를 들어 “첫 토큰을 정해진 시간 안에 받은 요청의 비율”은 측정 경계와 집계 기간을 정해야 운영 가능한 목표가 된다. [Google SRE의 서비스 수준 목표](https://sre.google/sre-book/service-level-objectives/)

Ragas나 DeepEval 같은 평가 도구는 실행과 보고를 도울 뿐이다. 어떤 실패를 허용할지, 어떤 사례를 사람이 검토할지는 서비스의 결정으로 남는다.

## Shadow, 카나리, A/B는 서로 다른 질문에 답한다

| 방식 | 사용자에게 보이는 응답 | 주된 목적 |
| --- | --- | --- |
| Shadow | 기존 버전의 응답 | 복제한 입력으로 후보의 실행·품질 비교 |
| 카나리 | 일부 트래픽에 후보 응답 | 영향 범위를 제한하며 출시 위험 확인 |
| A/B | 배정된 집단별 응답 | 사용자 결과의 차이를 실험으로 추정 |

SageMaker의 Shadow 배포도 후보 서빙 구성을 운영 승격 전에 검증하는 기능이다. **후보 응답을 사용자에게 보내지 않는 것과 운영 영향이 없는 것은 다르다.** 복제 실행은 자원을 소비하고, 도구가 결제·발송·수정을 수행하면 실제 부작용이 생길 수 있다. [SageMaker Shadow 배포](https://docs.aws.amazon.com/sagemaker/latest/dg/model-shadow-deployment.html)

따라서 이 글에서 제안하는 Shadow 환경은 쓰기 도구를 모의 실행하거나 격리된 대상에 연결하고, 별도 자원 한도와 시간 제한을 둔다. 다중 턴에서는 후보의 답이 다음 사용자 입력을 바꿀 수 있으므로, 기존 대화를 재생한 결과만으로 후보의 실제 사용자 경험을 판단하지 않는다.

카나리는 중단 기준과 이전 릴리스로의 복구 경로를 함께 준비한다. A/B는 사용자나 세션 단위의 일관된 배정과 충분한 관찰이 필요하다. 두 방식은 함께 사용할 수 있지만, 작은 트래픽에 배포했다는 사실만으로 통계적 비교가 성립하지는 않는다.

## 관측 결과를 다음 실험으로 돌려보내기

메트릭은 문제 규모를, 트레이스는 실패한 단계를, 로그는 구체적인 사건을 보여준다. 응답과 피드백을 `release_id`·trace ID에 연결하면 어떤 변경에서 문제가 생겼는지 좁힐 수 있다. 요청 ID나 사용자 ID를 메트릭 레이블로 무제한 추가하면 시계열 수가 급증하므로, 상세 식별자는 로그·트레이스에서 조회하는 구성을 우선 검토한다.

운영 피드백은 바로 학습 데이터가 되지 않는다. 이 글에서는 **수집 범위 확인 → 민감정보 최소화 → 중복 제거 → 원인 분류 → 검수 → 평가 또는 학습 편입**을 기본 흐름으로 제안한다. 검색 실패를 모델 재학습으로 해결하려 하거나 잘못된 사용자 피드백을 정답으로 굳히지 않도록 한다.

PII 탐지와 마스킹에도 누락이 있고, 해싱만으로 익명성이 보장되는 것은 아니다. 원문 보관 여부, 접근 권한, 보존 기간, 삭제 전파를 별도로 설계한다. 모델 제공자의 데이터 이용 조건도 제품·계약·설정에 따라 확인해야 하며 “모든 제공자가 운영 데이터를 학습하지 않는다”고 일반화할 수 없다.

처음에는 대표 업무 하나의 입력·산출물·판단 기준을 고정하고 같은 실험을 다시 실행할 수 있게 만드는 편이 좋다. 이후 평가 자동화, 릴리스 승인과 복구, 피드백 편입을 연결한다. 개선 속도는 실험 소요 시간, 회귀 발견 시간, 복구 시간과 함께 보며, 게이트 통과율 자체를 높이는 것을 목표로 삼지 않는다.
