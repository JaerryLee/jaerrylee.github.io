AGP Note는 팀의 회의 기록을 다음 업무로 연결하기 위해 개발한 데스크톱 앱이다. 회의를 전사한 뒤 사람이 검토하고, 결정 사항과 후속 작업을 정리해 Confluence와 Jira에 게시하는 흐름을 하나의 앱으로 묶었다.

팀 업무의 AX 전환에서 내가 맡은 일은 데스크톱 앱, 전사·검토·요약과 게시 기능, MCP 도구, Windows 설치·업데이트 흐름의 구현이었다. 이 글은 이전에 수행한 프로젝트에서 **생성 결과를 실제 업무에 쓰기 위해 보존해야 했던 정보와 실행 경계**를 정리한 기록이다.

## 전사 성공 다음에 남는 일이 많다

회의를 텍스트로 바꾸는 것만으로 회의록이 완성되지는 않는다. 화자가 잘못 나뉠 수 있고, 사용자가 이름과 문장을 교정해야 할 수도 있다. 요약에 포함된 결정이 어디에서 나온 것인지 확인해야 하며, 확정되지 않은 내용을 담당자의 업무로 등록해서도 안 된다.

그래서 회의 기록을 다음의 연결된 과정으로 다뤘다.

이 흐름을 데스크톱에서 제공하기 위해 Tauri·Svelte와 Rust를 사용하고 프로젝트·회의 기록과 작업 상태를 SQLite에 저장했다. 로컬 음성 모델과 API 전사를 모두 연결하되, 어떤 방식으로 처리하는지를 사용자가 확인할 수 있게 했다.

## 다시 분석해도 사용자의 교정본을 잃지 않게 한다

화자 분석을 다시 실행할 때 기존 전사까지 덮어쓰면 사람이 들인 검토 작업이 사라질 수 있다. 모델이 새 결과를 냈다는 사실이 기존 내용보다 무조건 낫다는 뜻은 아니다.

내가 구현한 검토 흐름은 원본 음성, 전사와 교정 내용을 구분하고 화자 재분석 과정에서 기존 전사·교정본을 보존하는 데 초점을 맞췄다. 사용자는 새 분석 결과를 확인하면서도 이전 기록을 기준으로 판단할 수 있어야 했다.

같은 이유로 작업 상태와 데이터의 존재 여부를 구분했다. 이전 전사가 남아 있다고 새 전사 작업이 성공한 것은 아니다. 실패·취소한 작업의 화면에 기존 결과가 보일 수 있으므로, 작업 ID와 최종 상태를 확인한 뒤 새 결과로 사용할지를 판단해야 한다.

이 구분은 AI 기능을 반복 실행할 수 있게 만드는 데 필요하다. 실패 후에도 이전 작업을 계속 사용할 수 있어야 재시도가 사용자에게 데이터 손실로 느껴지지 않는다.

## 요약과 게시할 내용에 같은 근거를 유지한다

요약은 전사 원본과 구간 정보에 연결했다. 회의에서 확정한 내용, 후속 작업, 아직 답이 없는 질문을 구분하고, 전사에 없는 담당자나 기한을 임의로 채우지 않도록 요약·게시 계약을 구성했다.

MCP에서 전사를 여러 번에 나눠 읽을 때는 revision을 함께 확인한다. 첫 부분을 읽은 뒤 원문이 수정됐는데 나머지를 그대로 이어 읽으면 서로 다른 버전의 전사가 하나의 요약에 섞일 수 있기 때문이다. 원문 버전이 바뀌면 다시 읽는 경로로 처리한다.

저장된 회의 요약에도 전사 변경 여부를 연결했다. 전사가 바뀐 뒤 오래된 요약을 그대로 게시하는 일을 막고, 게시 직전에 사용자가 확인한 내용과 실제 전송할 내용이 일치하는지 다시 검증했다.

## 미리보기와 외부 게시는 다른 작업이다

회의 요약을 저장하는 일과 Confluence 페이지나 Jira 이슈를 만드는 일은 나누었다. 미리보기를 열거나 문장을 편집하는 동작만으로 외부 게시가 실행되지는 않는다.

게시에서는 다음 순서가 중요했다.

1. 저장된 회의와 게시 대상의 정보를 읽어 미리보기를 만든다.
2. 사용자가 대상과 내용을 확인한다.
3. 게시 시점에 확인한 버전과 현재 버전이 같은지 검사한다.
4. 외부 요청의 결과와 원격 식별자를 게시 기록에 남긴다.

미리보기 이후 연결 설정이나 요약이 바뀌면 다시 확인하도록 했다. 확인한 내용과 전송한 내용이 달라지는 문제를 막기 위한 선택이다.

또한 같은 제목의 페이지가 있다는 이유로 임의의 원격 문서를 덮어쓰지 않았다. 회의별 게시 기록과 원격 식별자를 사용하고, 충돌하는 경우에는 사용자가 구분할 수 있도록 안내했다. Jira에는 선택한 후속 작업을 게시한다. 이 구조에서 원격 식별자는 단순한 결과 링크가 아니라 다음 게시와 복구의 기준이 된다.

## MCP에서도 접수와 완료를 구분한다

앱의 기능은 MCP를 통해 녹음 가져오기, 전사 준비·실행, 요약 저장과 게시 도구로도 제공했다. 여기서 중요한 점은 **도구 호출이 반환됐다는 사실과 실제 작업이 끝났다는 사실을 구분하는 것**이었다.

예를 들어 전사 시작 명령이 완료됐다는 응답은 전사 작업이 접수됐다는 뜻일 수 있다. 클라이언트는 명령 결과에서 작업 ID를 얻고, 작업 상태를 조회해 실제 전사 결과가 준비됐는지 확인해야 한다.

| 구분 | 의미 | 다음에 확인할 것 |
| --- | --- | --- |
| 명령 접수 | 앱이 요청을 받음 | 명령의 처리 결과 |
| 작업 시작 | 전사 작업이 만들어짐 | 작업 ID와 진행 상태 |
| 전사 완료 | 새 결과를 읽을 수 있음 | 결과 revision과 검토 내용 |
| 요약 저장 | 앱에 회의 기록이 저장됨 | 게시 여부와 게시 대상 |
| 외부 게시 | 원격 서비스에 반영됨 | 원격 링크와 게시 기록 |

요청과 결과를 SQLite에 남겨 MCP 클라이언트가 다시 연결해도 조회할 수 있게 했다. 응답이 불확실하면 같은 요청 ID와 같은 입력으로 재시도하고, 같은 ID에 다른 입력을 보내면 충돌로 처리한다.

앱이 종료돼 중단된 요청을 무조건 자동 재실행하지는 않는다. 이미 외부 API에 전송된 요청에는 비용이 발생했을 수 있기 때문이다. 기존 작업을 조회하고 상태를 확인한 뒤 새 실행을 결정할 수 있도록 했다. 프로젝트별 권한 역시 도구 목록을 보여줄 때뿐 아니라 실행 경계에서 확인한다.

## 설치 이후에도 이어지는 제품 경험

팀에서 사용하는 앱은 개발 환경에서 실행되는 것으로 끝나지 않는다. Windows 설치와 자동 업데이트, 업데이트가 중단된 뒤 다시 복구하는 흐름까지 구현했다.

업데이트 매니페스트의 서명 검증은 업데이트 정보의 신뢰성을 확인하는 장치다. Windows 설치 프로그램 자체의 코드 서명과는 다른 범위이므로 두 가지를 같은 기능으로 설명하지 않는다.

이 프로젝트에서는 녹음부터 전사·검토·요약·게시까지 이어지는 업무 흐름을 구현했다. AI가 만든 결과를 사람이 교정하고 확인한 뒤 기존 업무 도구에 반영할 수 있도록, 단계 사이의 원본과 상태를 보존하는 것이 핵심이었다.

현재의 [LLM 실행 관측 업무](/posts/llm-ops-opentelemetry/)에서도 이 경험이 이어진다. 작업이 시작됐는지, 결과가 준비됐는지, 외부에 반영됐는지를 구분하는 일은 제품 경험과 관측 모두에 필요하다.
