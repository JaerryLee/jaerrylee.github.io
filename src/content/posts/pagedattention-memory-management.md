PagedAttention의 핵심은 attention의 수학을 바꾸는 데 있지 않다. **요청의 KV 캐시가 하나의 큰 연속 공간에 있어야 한다는 제약을 풀어 같은 GPU 메모리에 더 많은 요청을 담는 것**이다.

이 글은 제공된 한국어 해설을 줄이고 원문과 대조한 연구 노트다. 대상은 Woosuk Kwon 외 8인의 *Efficient Memory Management for Large Language Model Serving with PagedAttention*, SOSP 2023이다. 실험 결과는 저자들의 보고이며 직접 재현한 수치가 아니다. [논문 원문](https://arxiv.org/abs/2309.06180)

## 캐시의 크기보다 할당 방식이 먼저 한계를 만들 수 있다

자동회귀 생성은 이전 위치의 key와 value를 재사용한다. 요청이 길어질수록 KV 캐시가 자라지만 출력 길이는 시작 시점에 정확히 알 수 없다. 최대 길이에 맞춰 요청별 연속 공간을 예약하면 아직 생성하지 않은 토큰의 공간까지 다른 요청이 사용하지 못한다.

논문은 이 문제를 예약 공간, 할당 내부의 미사용 공간, 할당 사이의 외부 단편화로 나누어 분석한다. 여러 출력을 생성할 때 같은 프롬프트의 캐시를 각 시퀀스에 복사하면 중복 저장도 생긴다. 가중치가 GPU에 들어간다는 사실만으로 충분한 동시 요청을 처리할 수 없는 이유다.

기존 Orca의 반복 단위 스케줄링은 완료된 요청을 빼고 새 요청을 넣는 문제를 다룬다. PagedAttention은 그 배치가 사용할 캐시 공간을 효율적으로 관리한다. 스케줄링과 메모리 관리는 함께 작동하는 요소다. [원문 §2–3](https://arxiv.org/pdf/2309.06180)

## 논리 순서와 물리 위치를 분리하기

KV 캐시를 고정 크기 블록으로 나누고, 시퀀스의 논리 블록을 실제 GPU 블록에 매핑한다. attention 커널이 이 블록 테이블을 읽어 필요한 KV를 찾으므로 물리 주소가 연속일 필요가 없다.

아래는 블록당 4토큰, 현재 7토큰인 경우를 설명하기 위한 예시다. 번호는 물리 위치를 구분하기 위한 임의의 값이다.

| 논리 블록 | 물리 블록 | 저장된 토큰 |
| --- | --- | --- |
| 0 | 7 | 1–4 |
| 1 | 1 | 5–7, 빈칸 1개 |
| 2 | 아직 없음 | 9번째 토큰을 저장할 때 할당 |

8번째 토큰은 남은 칸을 채우고, 9번째 토큰부터 새 블록을 받는다. 최대 출력 길이를 위한 공간을 요청마다 처음부터 예약하지 않는다. 같은 크기의 블록을 사용하는 풀 안에서는 외부 단편화를 없앨 수 있고, 단순한 단일 시퀀스의 미사용 슬롯은 마지막 블록에 남는다. 메타데이터나 런타임의 다른 메모리 낭비까지 사라진다는 뜻은 아니다.

블록별로 KV를 읽더라도 attention은 시퀀스 전체에 대한 정규화를 유지해야 한다. 각 블록을 독립적으로 softmax한 뒤 단순히 더하는 알고리즘으로 이해하면 잘못이다. [원문 §4.1–4.2](https://arxiv.org/pdf/2309.06180)

## 공유한 상태를 수정할 때만 복사하기

같은 프롬프트에서 여러 출력을 만들면 초기 KV 블록을 공유할 수 있다. 참조 횟수로 사용 중인 시퀀스를 추적하고, 공유 블록에 서로 다른 값을 써야 할 때만 복사하는 copy-on-write를 사용한다.

이 방식은 병렬 샘플링의 공통 프롬프트, 빔 탐색의 공통 조상, 요청 사이의 공통 prefix에 적용된다. 다만 의미가 비슷한 두 문장의 캐시를 섞어 쓰는 것은 아니다. 실제로 재사용 가능한 동일 상태여야 한다.

빔 후보가 사라지면 참조 횟수를 줄이고 더 이상 사용하는 후보가 없는 블록을 반환한다. 원문의 `fork`, `append`, `free` 인터페이스는 이러한 시퀀스 생성·확장·해제를 메모리 관리와 연결한다. [원문 §4.3·§5](https://arxiv.org/pdf/2309.06180)

## 메모리가 모자라면 선점과 복구가 필요하다

블록 할당이 효율적이어도 메모리 자체는 유한하다. 논문의 시스템은 캐시가 부족할 때 요청을 선점하고, CPU 메모리로 옮긴 캐시를 복구하거나 기존 토큰을 다시 처리해 캐시를 재계산한다. full attention에서 필요한 과거 KV를 일부만 잃은 채 같은 계산을 계속할 수 없으므로, 논문은 시퀀스와 캐시를 공유하는 그룹을 함께 다룬다.

분산 실행에서는 스케줄러가 실행할 시퀀스와 블록 매핑을 정하고 GPU worker가 각자의 모델 분할을 실행한다. 비연속 접근의 비용은 KV 쓰기, 블록 읽기와 attention, 블록 복사를 묶은 커널로 줄인다. [원문 §4.5–5](https://arxiv.org/pdf/2309.06180)

이 설명을 현재 vLLM의 모든 실행 경로와 동일시하면 안 된다. 예를 들어 확인한 V1 문서는 기본 선점 복구 방식으로 `RECOMPUTE`를 설명한다. 블록 크기·attention backend·스케줄링은 사용 버전과 모델 조건에서 확인해야 한다. [vLLM 선점·튜닝 문서](https://docs.vllm.ai/en/stable/configuration/optimization/)

## 논문의 숫자는 무엇을 측정했나

| 원문 결과 | 해석할 때 붙여야 하는 조건 |
| --- | --- |
| 동일 지연 수준에서 처리량 2–4배 개선 | 당시 FasterTransformer·Orca 계열과 비교한 전체 시스템 결과 |
| 실제 토큰 상태가 KV 공간의 96.3% | Figure 2의 실험 평균이며 전체 GPU VRAM 사용률이 아님 |
| attention 커널 지연 20–26% 증가 | Figure 18a의 FasterTransformer 대비 커널 비교 |

주요 평가는 A100, OPT·LLaMA 계열, ShareGPT·Alpaca 길이 분포와 합성 도착 트래픽을 사용했다. Orca는 저자들이 재구현했고, 실제 출력 길이를 미리 안다고 가정한 Oracle 변형도 포함했다. 특정 비교에서 나온 최대 배율을 일반적인 서비스 개선 폭으로 옮기면 안 된다. [원문 Figure 2·§6·Figure 18](https://arxiv.org/pdf/2309.06180)

평가의 정규화 지연은 **요청별 종단간 지연을 출력 토큰 수로 나눈 뒤 평균한 값**이다. 첫 토큰 이후만 보는 TPOT와 다르다. 또한 커널은 느려졌는데 시스템 처리량은 좋아졌다는 결과는 모순이 아니다. 캐시 낭비를 줄여 더 큰 배치를 처리한 이득이 추가 주소 조회 비용을 상쇄한 것이다.

블록 크기 역시 절충이다. 작은 블록은 GPU 병렬성을 충분히 활용하기 어렵고, 큰 블록은 미사용 슬롯을 늘리고 공유 기회를 줄인다. 논문 구현은 16토큰을 기본값으로 택했지만 모든 현재 모델·backend의 최적값을 의미하지 않는다. [원문 §7.2](https://arxiv.org/pdf/2309.06180)

## 현재 시스템에 가져올 설계 질문

논문을 적용할 때는 “vLLM이면 몇 배 빠르다” 대신 다음을 확인하는 것이 유용하다.

1. 동시 요청을 막는 원인이 캐시 용량·단편화인가, 연산·대역폭·큐 대기인가?
2. 긴 문맥과 공통 prefix가 실제 트래픽에서 얼마나 자주 나타나는가?
3. 블록 크기를 바꾸면 마지막 블록의 낭비와 커널·메타데이터 비용이 어떻게 달라지는가?
4. 늘어난 처리량이 TTFT·생성 지연 목표를 지키면서 얻어진 것인가?

FlashAttention은 attention 연산의 메모리 I/O를, PagedAttention은 동적으로 유지되는 KV 상태의 배치와 공유를 다룬다. 두 관점은 함께 사용할 수 있다. 전체 메모리 예산과 부하 측정 방법은 [서빙 성능 글](/posts/llm-serving-performance/)로 이어진다.
