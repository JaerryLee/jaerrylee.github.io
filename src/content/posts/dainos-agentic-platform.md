Dainos는 메일과 문서를 업무와 지식으로 연결하는 에이전틱 AI 플랫폼이다. 나는 에이전트 실행 기반을 개발하고, React 웹 콘솔과 FastAPI BFF, 지식 서비스의 API·권한·작업 처리를 제품 흐름으로 연결했다.

에이전트가 답을 한 번 생성하는 것과 사용자가 업무에서 반복해서 사용하는 기능을 만드는 것은 요구하는 상태가 다르다. 사용자의 실행이 어느 세션에 속하는지, 승인을 기다리는지, 지식화 작업이 끝났는지, 답변의 근거에 접근할 수 있는지까지 이어져야 한다.

이 글은 이전 프로젝트에서 맡았던 실행 기반과 제품 통합을 정리한다. 에이전트 런타임의 개발 이력과 현재 지식 질의 경로는 구분해서 설명한다.

## 실행 기반과 제품의 책임을 나눈다

에이전트 개발에서는 코어와 오케스트레이터의 책임을 분리했다. 모델·도구 실행을 다루는 부분과 세션·이벤트·실행 수명주기를 다루는 부분을 나누고, HTTP와 SSE를 통해 실행 결과를 전달했다.

제품 통합에서는 FE, BFF, KB Service와 KB Core의 역할을 구분했다.

| 계층 | 이 프로젝트에서 구분한 책임 |
| --- | --- |
| FE | 메일·업무·문서 탐색, 진행 상황과 답변·출처 표시 |
| BFF | 브라우저 요청을 제품 서비스와 연결하고 화면에 필요한 응답 조합 |
| KB Service | 제품 API, 인증·권한, 지식화 작업과 멱등성 정책 |
| KB Core | 지식의 의미 처리와 핵심 저장·질의 기능 |

내 기여의 중심은 실행 기반, FE·BFF와 KB Service의 제품 통합이다. KB Core가 제공하는 지식 처리 기능을 제품의 권한과 API 계약에 맞춰 연결하는 역할을 맡았다.

## 승인 대기는 실행 실패가 아니다

에이전트가 도구를 호출하기 전에 사용자의 승인이 필요한 경우가 있다. 이 상태를 예외로만 다루면 실행이 실패했는지, 사용자 입력을 기다리는지 구분하기 어렵다. 반대로 승인 없이 자동으로 다음 단계로 진행하면 사용자가 실행을 제어할 수 없다.

승인이 필요한 도구에 대해 실행을 중단하고 승인 결과를 받은 뒤 재개하는 흐름을 구현했다. 세션과 이벤트는 사용자가 무엇을 요청했고 현재 어떤 결정을 기다리는지 연결하는 기준이다.

이때 세션과 지식·메모리의 사용자 범위를 함께 분리했다. 세션 ID를 알고 있다는 이유만으로 다른 사용자의 실행을 읽거나 이어갈 수 있어서는 안 된다. 실행을 식별하는 것과 그 실행에 접근할 권한이 있는 것은 다른 검사다.

SSE는 진행 중인 응답을 전달하는 수단으로 사용했다. 하지만 연결이 닫혔다는 사실만으로 전체 실행이 성공했다고 판단할 수는 없다. 제품에서는 전달 상태와 저장된 실행 상태를 구분하고, 사용자에게 최종 결과를 확인할 수 있는 경로가 필요하다.

## 메일에서 근거 있는 답변까지 연결한다

사용자에게 중요한 것은 서비스의 개수보다 메일을 선택한 뒤 무엇을 할 수 있는지다. 메일과 문서를 지식화하고, 관련 업무와 문서를 탐색한 다음 근거를 확인하며 질문하는 흐름을 FE와 BFF에서 연결했다.

현재 문서에서 확인한 지식 질의의 주요 경로는 BFF → KB Service → KB Core다. 과거에 개발한 에이전트 실행 기반을 이 경로의 필수 중간 단계처럼 그리지 않았다. 전환 중인 플랫폼에서는 예전 구성과 현재 제품의 실제 호출 경로를 섞지 않는 것이 중요하다.

답변의 근거도 화면의 부가 정보로만 다루기 어렵다. 관련 문서를 찾고 출처를 표시하더라도 사용자가 해당 업무나 문서에 접근할 수 있는 범위와 맞아야 한다. 그래서 제품 API와 권한 처리는 지식 서비스의 책임에 포함했다.

## 오래 걸리는 지식화 작업은 상태를 남겨야 한다

지식화는 API 요청 하나가 끝나는 동안 완료되지 않을 수 있다. 작업의 접수·실행·중단·재시도와 최종 결과를 사용자 화면까지 전달해야 한다. 나는 KB Service에서 작업의 영속 상태와 멱등 재시도, 중단 후 재개 처리를 구현했다.

작업 저장과 메시지 전달은 서로 다른 경계다. 처리 중 서비스가 종료되거나 메시지가 다시 전달될 때 어느 단계까지 반영됐는지 확인할 수 있어야 한다. 이를 위해 구현에는 다음과 같은 역할을 분리했다.

| 장치 | 필요한 이유 |
| --- | --- |
| 영속 작업·실행 상태 | 프로세스 메모리 밖에 진행·실패·완료의 근거 보존 |
| lease와 실행 주체 확인 | 특정 작업을 처리할 수 있는 실행의 범위 제어 |
| 적용 journal | 데이터에 반영한 단계와 복구 판단의 근거 기록 |
| 상태 outbox | 저장한 상태와 외부로 전달할 이벤트의 연결 관리 |
| 멱등 처리와 redrive | 같은 작업이 다시 도착하거나 중단된 작업을 재개하는 경로 관리 |

핵심은 재시도 횟수를 늘리는 것보다 재시도할 때 이미 적용된 결과를 어떻게 판단할지 정하는 데 있었다. 또한 서비스가 작업 완료를 기록해도 브라우저가 마지막 이벤트를 받지 못할 수 있으므로, FE에서 최종 상태를 확인하는 흐름까지 연결했다.

이 구조의 운영 검증에서는 중단 지점별로 복구 시간과 중복·누락 여부를 확인해야 한다. lease를 얻은 직후, 데이터 반영 직후, 상태 전달 직전의 중단은 복구 판단이 서로 다르다. 프로젝트 기록에는 구현한 복구 경계와 추가 실연동 검증이 필요한 항목을 함께 남겼다.

## API 계약은 계층 사이의 변경을 드러낸다

여러 서비스가 함께 바뀌면 작은 응답 변경도 화면까지 영향을 준다. 예를 들어 작업 상태 enum이나 응답 필드가 달라졌는데 BFF가 이전 형태를 계속 반환하면, 서버에서는 작업이 끝났어도 화면은 대기 상태로 남을 수 있다.

FE–BFF–KB Service–Core 사이의 OpenAPI와 응답 모델을 맞추는 작업을 맡았다. 계약 산출물과 구현을 비교하고, 서비스 경계에서 응답을 검증하며, 제품 API와 내부 처리 모델을 구분하는 방식으로 변경을 드러냈다.

계약 검사는 실제 모델 응답의 품질이나 전체 배포 상태를 대신 검증하지 않는다. 대신 어느 계층에서 요청과 응답이 어긋나는지를 빠르게 좁히는 기준이 된다. 개발 환경의 배포 연동도 이 계약과 대표 사용자 흐름을 함께 확인하는 작업으로 다뤘다.

## 제품으로 연결하며 남긴 기준

이 프로젝트에서 구현한 것은 에이전트의 단일 답변보다 넓은 범위였다. 세션과 승인·재개, 메일·업무·문서 탐색, 지식화 작업과 근거 기반 채팅이 사용자의 권한과 상태 안에서 연결되도록 했다.

앞으로 비슷한 플랫폼을 설계한다면 데이터의 소유권, 접근 범위, 작업의 완료 기준과 대표 사용자 여정을 먼저 정할 것이다. 비슷한 화면을 보여주는 데이터라도 생성 경로와 수명주기가 다를 수 있기 때문이다.

현재의 [LLM Ops 업무](/posts/llm-ops-opentelemetry/)에서는 이 서비스 경계와 실행 상태를 관측 데이터로 이어가는 데 집중하고 있다. 제품을 연결할 때 정의한 책임과 완료 기준이 있어야, 로그와 트레이스에서도 무엇을 확인해야 하는지 명확해진다.
