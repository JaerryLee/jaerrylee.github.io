답변이 틀렸을 때 모델부터 교체하면 검색 누락, 오래된 문서, 잘못된 도구 실행을 놓칠 수 있다. **입력 구성 → 검색 → 흐름 선택 → 모델 호출 → 출력·행동 검증**으로 나누어 실패 지점을 찾는 편이 개선 대상을 좁히기 쉽다. 다음 내용은 학습 자료와 원 연구를 비교해 정리한 설계 기준이다.

## 토큰과 생성 설정도 입력 계약이다

토크나이저는 텍스트를 토큰 ID로 바꾼다. 토큰은 단어나 글자와 일대일로 대응하지 않으며 같은 문장도 모델에 따라 길이가 달라진다. 서빙에서는 모델과 호환되는 tokenizer와 chat template을 사용하고, 지시·대화 이력·검색 문서·출력 예산을 함께 계산한다. 한도 초과를 오류로 처리할지 잘라낼지는 엔진·애플리케이션 설정에 따라 다르므로 명시적인 정책이 필요하다.

일반적인 decoder-only Transformer는 causal attention으로 이전 위치의 표현을 참조하고 다음 토큰의 분포를 계산한다. `temperature`는 그 분포를 조절하고, `top-k`는 후보 개수를, `top-p`는 누적 확률에 따른 후보 범위를 제한한다. 낮은 temperature가 사실성이나 안전성을 보장하지 않으며 완전한 재현성도 별도로 확인해야 한다. [Transformers 생성 설정](https://huggingface.co/docs/transformers/main_classes/text_generation), [vLLM 재현성 조건](https://docs.vllm.ai/en/stable/usage/reproducibility/)

프롬프트에는 목표, 제약, 필요한 맥락, 예시, 출력 계약을 구분해 둔다. zero-shot과 few-shot은 예시 제공 여부의 차이다. JSON 스키마를 만족하는 응답도 값이 틀리거나 실행 권한을 위반할 수 있으므로, 파싱·스키마 검사 뒤에 업무 규칙 검증이 필요하다.

## 추론 기법은 추가 계산을 어디에 쓸지 정한다

| 연구·패턴 | 핵심 아이디어 | 운영에서 비교할 것 |
| --- | --- | --- |
| [Chain-of-Thought](https://arxiv.org/abs/2201.11903) | 중간 풀이가 포함된 예시로 다단계 문제 해결 유도 | 해당 모델·업무의 정답률과 출력 비용 |
| [Self-Consistency](https://arxiv.org/abs/2203.11171) | 여러 추론 경로를 샘플링해 답을 집계 | 추가 호출 비용, 서로 연관된 오류 |
| [Tree of Thoughts](https://arxiv.org/abs/2305.10601) | 중간 후보를 생성·평가하며 탐색 | 탐색 폭·깊이·중단 조건 |
| [ReAct](https://arxiv.org/abs/2210.03629) | 추론과 외부 행동·관측을 번갈아 수행 | 도구 성공률, 반복 횟수, 실행 권한 |

이 연구들의 특정 벤치마크 개선을 모든 모델의 필수 프롬프트 규칙으로 옮기지는 않는다. 자체적인 추론 방식을 가진 모델도 있으므로 지원하는 사용 방식으로 비교한다. 자기 비평이나 긴 풀이가 있다는 사실만으로 답이 검증되는 것은 아니다. 최종 답과 근거, 실제 작업 결과를 평가해야 한다.

## 검색은 문서 정리부터 평가한다

RAG는 검색한 외부 정보를 생성의 문맥에 넣는 방식이다. 별도 벡터 DB가 필수인 것은 아니며 키워드 검색이나 기존 데이터베이스도 검색 경로가 될 수 있다. 원 RAG 연구는 매개변수에 저장된 지식과 검색 가능한 비매개변수 메모리의 결합을 제안했다. [RAG 논문](https://arxiv.org/abs/2005.11401)

청크 크기는 고정 정답이 없다. 제목·문단·표의 의미 단위를 보존하면서 검색 누락과 불필요한 문맥, 토큰 비용을 비교한다. 출처 ID, 원문 위치, 문서 버전, 접근 권한을 청크와 함께 유지해야 인용·삭제·재색인이 가능하다.

BM25 같은 어휘 검색은 용어·식별자 일치를, dense retrieval은 학습된 의미 유사성을 활용한다. 두 결과를 합칠 때 RRF는 서로 다른 점수의 크기를 직접 비교하는 대신 순위를 결합한다. [Elasticsearch RRF 설명](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

Cross-Encoder reranker는 질문과 후보 문서를 함께 평가하지만, 첫 검색에서 누락한 문서를 되살릴 수는 없다. [Sentence Transformers의 Cross-Encoder 설명](https://sbert.net/examples/cross_encoder/applications/README.html)

| 인덱스 기법 | 줄이려는 비용 | 주요 절충 |
| --- | --- | --- |
| HNSW | 그래프 탐색으로 비교할 벡터 수 축소 | 그래프 메모리, 구축 비용, 탐색 범위와 recall |
| IVF | 벡터 공간을 나누고 일부 목록만 검색 | 탐색 목록 수, 데이터 분포, 학습된 분할 품질 |
| PQ | 벡터를 짧은 코드로 압축 | 저장량과 거리 근사의 오차 |

IVF와 PQ는 결합할 수 있다. 근사 최근접 검색(ANN)의 recall은 정확 검색 결과를 얼마나 재현하는지이며, 업무상 정답 문서를 찾는 retrieval recall과는 평가 대상이 다르다. 둘을 같은 숫자로 취급하지 않는다. [Faiss 인덱스 설명](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)

임베딩 모델이 바뀌면 차원이 같아도 벡터 공간이 호환된다고 가정할 수 없다. 문서·질의 인코더의 호환성을 확인하고, 필요하면 문서를 다시 임베딩해 별도 인덱스에서 검증한 뒤 전환한다. 단순 문서 수정은 영향받는 청크만 갱신할 수 있다. 삭제·권한 변경은 검색 결과뿐 아니라 캐시에도 반영해야 한다.

## 고급 RAG는 서로 다른 실패를 겨냥한다

| 접근 | 연구에서 제안한 변화 | 적용 전 질문 |
| --- | --- | --- |
| [HyDE](https://arxiv.org/abs/2212.10496) | 가상 문서를 생성·임베딩해 실제 문서 검색 | 가상 문서를 사실 근거로 잘못 사용하지 않는가? |
| [Self-RAG](https://arxiv.org/abs/2310.11511) | 검색과 자기 점검을 특수 토큰으로 학습 | 단순한 자기 비평 프롬프트와 구분했는가? |
| [CRAG](https://arxiv.org/abs/2401.15884) | 검색 결과를 평가해 보완 검색 등을 선택 | 검색 평가기의 오류와 외부 검색 범위는? |
| [GraphRAG](https://arxiv.org/abs/2404.16130) | 엔터티 그래프·커뮤니티 요약으로 전체 문서군 질문 처리 | 그래프 구축·갱신 비용을 감당할 업무인가? |

Multi-hop 검색은 여러 근거를 순차적으로 연결하고, agentic 검색은 중간 결과에 따라 다음 검색을 선택한다. 모든 요청을 이 흐름으로 바꾸기보다 단일 검색으로 실패한 유형에서 추가 지연·비용 대비 효과를 확인한다. GraphRAG도 모든 사실 조회에서 일반 RAG보다 우수하다는 의미는 아니다.

## 에이전트의 도구 호출은 실행 요청이다

고정 workflow는 코드가 순서를 결정하고, 라우터는 분기를 선택하며, 에이전트는 관측 결과에 따라 다음 행동을 선택한다. LangChain·LlamaIndex·Semantic Kernel 같은 프레임워크 이름보다 상태 저장, 취소, 재시도, 스트리밍, 장애 복구가 어디에서 책임지는지 먼저 정한다.

모델이 생성한 도구 이름과 인자는 신뢰할 수 없는 실행 요청으로 다룬다. 애플리케이션이 스키마, 사용자 권한, 대상 리소스, 업무 조건을 검사한 뒤 실행해야 한다. 재시도에는 횟수·시간 예산과 backoff를 두고, 쓰기 작업은 idempotency key나 중복 확인으로 부작용을 관리한다. timeout을 받았다고 외부 작업이 실패했다고 단정할 수는 없다.

MCP는 host·client·server와 도구·리소스 등의 교환 방식을 정의한다. **MCP로 연결했다는 사실이 인증·인가나 샌드박스 격리를 대신하지 않는다.** 이 글에서 제안하는 실행 정책은 최대 단계·토큰·시간·비용과 도구별 권한을 함께 제한하는 것이다. [MCP 아키텍처](https://modelcontextprotocol.io/docs/learn/architecture)

여러 에이전트를 쓰면 역할 분리가 가능하지만 호출 수와 상태·권한 경계도 늘어난다. 감독자, 계층형, 토론형 구조 모두 먼저 단일 에이전트나 고정 workflow를 기준선으로 두고 작업 성공률과 총비용을 비교해야 한다.

## 입력 필터보다 실제 권한 경계가 중요하다

검색 문서와 도구 결과에도 프롬프트 인젝션이 들어올 수 있다. 사용자 입력 검사만으로 방어가 끝나지 않으며, 시스템 프롬프트에 “무시하라”고 쓰는 것만으로 권한이 생기거나 보호되지 않는다.

문서 접근 범위는 검색 시 제한하고 모델에 넘기기 전에도 검증한다. 도구 실행기는 최소 권한으로 동작하고, 민감한 쓰기 작업에는 업무에 맞는 승인·감사 경로를 둔다. guardrail 모델도 우회되거나 오판할 수 있어 이러한 경계를 대체할 수 없다. [OWASP 프롬프트 인젝션 방어](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

답변의 출처 링크가 실제 주장을 뒷받침하는지, 근거가 없을 때 보류하는지, 권한 없는 자료를 요청하면 차단하는지를 각각 평가한다. 검색·생성·행동의 점수를 분리한 뒤 [운영 평가와 출시 게이트](/posts/llmops-operating-loop/)에 연결하면 개선해야 할 단계가 선명해진다.
