SFT, LoRA, DPO는 같은 종류의 선택지가 아니다. SFT와 DPO는 학습 신호와 목적에 관한 방법이고, LoRA는 어떤 파라미터를 갱신할지 정하는 방법이다. 따라서 **LoRA로 SFT를 수행하거나 LoRA로 DPO를 수행할 수 있다.** 이 구분부터 해야 학습 파이프라인의 입력과 산출물을 정확히 기록할 수 있다.

이 글은 후학습 자료를 원 논문과 대조한 연구·설계 노트다. 특정 모델에서 직접 재현한 성능 수치를 제시하는 글은 아니다.

## 모델을 바꿔야 하는 문제인지 먼저 확인하기

지시가 모호하면 프롬프트와 출력 계약을, 필요한 문서가 빠졌으면 검색을 먼저 점검한다. 반복되는 작업 형식이나 도메인 행동을 모델에 반영해야 한다면 후학습을 비교한다. 다만 “지식은 RAG, 행동은 튜닝”은 출발점을 고르는 휴리스틱이다. 튜닝도 지식을 학습할 수 있고, RAG에도 검색·근거 활용 능력을 높이는 학습이 적용될 수 있다.

사전학습, SFT, 선호 학습, rollout, 서비스 추론을 모든 프로젝트가 차례대로 거치는 필수 단계로 생각할 필요도 없다. 기존 instruct 모델을 그대로 사용할 수 있고, rollout은 평가에서도 학습용 데이터 생성에서도 쓰인다.

## 학습 목표와 피드백 출처 구분하기

| 방식 | 주요 입력 | 바꾸려는 것 |
| --- | --- | --- |
| 사전학습·계속 사전학습 | 텍스트·코드 등의 토큰 시퀀스 | 다음 토큰 예측을 통해 일반·도메인 표현 학습 |
| SFT | 입력과 목표 출력 | 원하는 지시 수행과 응답 패턴 |
| 선호 학습 | 같은 입력에 대한 선호·비선호 응답 | 상대적으로 선호하는 행동 |
| 강화학습 | 생성한 결과·행동과 보상 | 보상을 높이는 정책 |

대표적인 RLHF 구성은 SFT 이후 사람의 선호 비교로 보상 모델을 만들고, 그 보상을 이용해 정책을 최적화한다. InstructGPT는 이러한 흐름을 보여준다. 그러나 **RLHF가 언제나 PPO 하나만을 뜻하는 것은 아니다.** 피드백의 출처와 최적화 알고리즘을 구분해서 기록한다. [InstructGPT 논문](https://arxiv.org/abs/2203.02155)

DPO는 선호쌍을 이용해 정책을 직접 최적화하며, 원래 제안된 구성에서는 별도 보상 모델 학습이나 학습 중 온라인 샘플링 루프가 필요하지 않다. 기준 정책과의 관계를 포함한 목적함수이지, 좋은 답의 빈도만 늘리는 SFT와 동일하지 않다. 데이터 밖의 행동이나 안전성까지 자동으로 보장하지도 않는다. [DPO 논문](https://arxiv.org/abs/2305.18290)

RLAIF는 AI가 만든 피드백을 사용하는 방향을 말한다. Constitutional AI는 원칙에 따른 자기 비평·수정과 AI 선호를 학습에 사용한 사례다. 피드백을 AI로 만들더라도 원칙, 평가 모델, 데이터 분포의 편향을 검증해야 한다. [Constitutional AI 논문](https://arxiv.org/abs/2212.08073)

## LoRA와 QLoRA가 절약하는 것

LoRA는 기본 가중치를 고정하고 저랭크 행렬로 표현한 갱신분을 학습한다. 학습할 파라미터와 그 gradient·optimizer state를 줄이지만, 기본 모델을 실행하는 비용과 activation 메모리까지 없어지는 것은 아니다. rank, 적용 레이어, 학습률에 따라 결과가 달라진다. [LoRA 논문](https://arxiv.org/abs/2106.09685)

QLoRA는 동결한 기본 모델을 4비트로 저장하고 그 위에 LoRA를 학습한다. 원 논문은 NF4, double quantization, paged optimizer를 제안했다. **모든 연산과 학습 파라미터를 4비트로 갱신한다는 뜻은 아니다.** 여기서 paged optimizer는 학습 중 메모리 급증을 다루며, 서빙 KV 캐시를 관리하는 PagedAttention과는 다른 기술이다. [QLoRA 논문](https://arxiv.org/abs/2305.14314)

실험 결과와 함께 base model revision, tokenizer·chat template, adapter 설정, 정밀도, 라이브러리·드라이버 버전을 남긴다. adapter는 호환되는 기본 모델이 필요하다. 병합·양자화·서빙 엔진 변경 후에도 평가를 다시 수행해야 학습 환경에서 얻은 결과가 실제 배포에 이어지는지 확인할 수 있다.

PEFT는 LoRA뿐 아니라 prompt/prefix tuning, IA3처럼 일부 파라미터를 조정하는 방법들을 포괄한다. 작은 데이터라고 항상 LoRA가 최선이거나 full fine-tuning이 반드시 마지막 선택인 것은 아니다. 목표 품질, 메모리, 학습·배포 비용을 같은 기준으로 비교한다. [PEFT 문서](https://huggingface.co/docs/peft/en/index)

## 데이터 계약은 포맷 검사보다 넓다

학습용 JSON이 파싱된다고 데이터 준비가 끝난 것은 아니다. 다음 항목을 데이터셋 버전과 연결하는 방식을 제안한다.

| 관리 항목 | 기록할 내용 |
| --- | --- |
| 출처와 사용 범위 | 원천 ID, 수집 시점, 이용 가능 범위, 민감정보 처리 |
| 정제 | 필터 버전, 중복 제거 기준, 제외 사유, 샘플 수 변화 |
| 학습 표현 | 역할 구분, chat template, 종료 토큰, loss를 적용할 구간 |
| 분할 | 문서·사용자·시점별 train/validation/test 경계 |
| 선호 라벨 | 비교 기준, 평가자·모델 버전, 동률과 불일치 처리 |
| 합성 데이터 | 생성 모델·프롬프트, 검증 방식, 원본과의 중복 |

SFT에서는 assistant 응답에만 loss를 줄지 전체 시퀀스에 줄지 같은 선택도 학습 결과를 바꾼다. 대화 packing을 사용할 때는 라이브러리가 샘플 경계와 attention mask를 어떻게 처리하는지 확인한다. [TRL SFT Trainer](https://huggingface.co/docs/trl/en/sft_trainer)

선호쌍은 같은 질문·조건에 대한 비교인지, 길이나 말투가 정답성을 대신한 라벨인지 검수한다.

합성 데이터는 다양성을 늘릴 수 있지만 생성 모델의 오류도 반복한다. 새로운 샘플이 독립적인 지식인지 단순한 표현 변형인지 구분하고, 평가 정답을 학습 프롬프트에 노출하지 않는다. 운영 로그 역시 승인된 범위에서 정제·검수한 뒤 편입한다.

## Rollout과 verifier도 실험 자산이다

Rollout은 정책이 응답이나 행동 시퀀스를 생성한 기록이다. 반드시 도구를 쓰는 에이전트 실행일 필요는 없다. 도구를 사용한다면 관측, 호출 인자, 반환값, 종료 이유, 보상을 연결해야 실패를 재현할 수 있다.

| 용어 | 운영에서 확인할 점 |
| --- | --- |
| On-policy | 데이터를 만든 정책이 갱신 대상 정책과 얼마나 일치하는가 |
| Off-policy·과거 데이터 | 생성 정책·시점과 재사용 조건이 남아 있는가 |
| Verifier | 정답 비교·테스트·모델 판정 중 무엇을 검증하는가 |
| Reward | verifier 결과를 어떤 규칙으로 점수화하는가 |

비동기 수집에서는 정책이 갱신되는 동안 이전 버전의 rollout이 도착할 수 있다. 생성 모델 revision과 샘플링 설정을 남겨 데이터의 정책 차이를 확인한다. GRPO 같은 방법도 이러한 정책 최적화의 한 선택지이며, 모든 rollout에 같은 학습 알고리즘을 적용하는 것은 아니다. [DeepSeekMath의 GRPO](https://arxiv.org/abs/2402.03300)

실행 가능한 테스트나 수학 정답 비교는 강한 신호지만 불완전한 테스트와 비교 규칙에도 허점이 있다. 모델 judge는 선호를 측정할 수 있어도 정답을 보증하지 않는다. 이 글에서 제안하는 운영 기준은 보상 구성요소별 점수, verifier 실패, 시간 초과, 의심스러운 고득점 사례를 따로 기록하는 것이다.

샌드박스에는 파일·네트워크·비밀정보 접근 범위와 시간·자원 한도를 둔다. 격리 환경이 있다는 이유만으로 탈출이나 외부 부작용이 불가능하다고 가정하지 않는다. [도구 실행의 권한 경계](/posts/llmops-rag-agent-design/)도 함께 적용해야 한다.

## 재현과 회귀 확인을 출시 조건으로 삼기

동일한 시드를 저장해도 하드웨어, 커널, 병렬 실행, 라이브러리가 달라지면 결과가 완전히 같지 않을 수 있다. 데이터·코드·환경·설정을 고정하고 반복 실행에서 관측한 변동을 기록하는 것이 실용적인 재현 기준이다.

모델을 계속 갱신할 때는 새 업무 점수와 기존 능력의 회귀를 함께 확인한다. 과거 데이터 재사용이나 정규화 기법은 망각을 줄이기 위한 후보이지, 무조건 적용하는 규칙이 아니다. 최종 adapter·checkpoint와 평가 보고서를 연결한 뒤 [릴리스 게이트와 롤백 절차](/posts/llmops-operating-loop/)로 넘긴다.
